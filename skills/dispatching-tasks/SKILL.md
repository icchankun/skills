# dispatching-tasks

指令役は、作業を受け取って worktree に渡すところまでを受け持つ。実装はしない。

## 手順

1. **チケットを読む。** リンクがあれば中身を読み、要件・受け入れ条件・関連するリンクを拾う。曖昧な点があれば、ここでユーザーに聞く。渡した後に聞き直すより早い。
   - 「なぜ」（背景・課題・対応方針）もここで決める。チケットに書いてあれば、それを見せて合っているか確かめる。なければ聞く。自明なら聞かない。なぜはエージェントが考えるものではなく、人間が決めるもののため。
   - なぜが曖昧なとき（背景か課題か対応方針のどれかが抜けている、読み方が2通りある、答えを聞いても決まらない）は、`grilling` skill で詰める。詰めるのはなぜだけにし、実装の細部は driver に任せる。実装を始めてからなぜが揺らぐと、作り直しになるため。
2. **ブランチと worktree を作る。** `creating-git-branches` を呼ぶ。
   - Herdr.app の中なら、`git wt` のフックが worktree を Herdr.app の space として開き、最初のタブで driver を起動する。driver は Claude Code で、`git config --global herdr.driver codex` なら Codex になる。フックの出力に `driver: <番地> (<agent>)` が出る。
   - 出なければ、`hc ls --label role=driver` で、cwd が worktree のパスと一致する terminal を探す。
3. **引き継ぐ。** `handover <番地>` を呼ぶ。引き継ぎには次を入れる。
   - チケットの URL と、1 で拾った要件・受け入れ条件・なぜ
   - 決めたこと、聞いて答えをもらったこと
   - 最初にやること: `running-dev-flow` を使って進める
4. **手を離す。** 誰に何を渡したかをユーザーに伝えて終える。以降のやりとりは、引き継いだ先のペインで行う。このあと PR を出す・直すなど作業の続きを頼まれたら、自分では手を付けない。`hc send <driver の番地>` で driver に回し、回したことをユーザーに伝える。

## Herdr.app の外にいるとき

`HC_TERMINAL_ID` がなければ、driver は立たない。worktree のパスを伝え、そこで新しいセッションを開いて `running-dev-flow` で進めるよう伝えて終える。

## 規律

- 実装しない。指令役のセッションに実装の文脈を積むと、引き継ぐ量が増え、二重に作業が進む。
- 引き継ぎ先が見つからないまま `handover` しない。宛先のない引き継ぎは読まれない。
