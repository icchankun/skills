# PRレビュースレッド対応

依存: `gh` CLI（認証済み）、`ruby`

```
/resolving-pr-reviews 123         # 指摘がなくなるまで繰り返す
/resolving-pr-reviews 123 --once  # 1ラウンドで終える
```

## 全体の流れ

```
 ┌─► 1. 未解決スレッド取得 ── 0件 ──► 7. 結果報告
 │        │
 │   2. 仕分け（直す / 直さない / ユーザーに聞く）
 │        │
 │   3. 実装 → コミット
 │        │
 │   4. push の承認 ◄── ユーザー確認はここだけ
 │        │
 │   5. push → 返信 → resolve
 │        │
 │   6. Copilot に再レビュー依頼 → 届くまで待つ
 └────────┘
```

ユーザーに止めて確認を取るのは、ステップ4の push 前と、ステップ2で判断が要る指摘があったときだけ。

`--once` のとき、または PR に Copilot のレビューが付いていないときは、ステップ5で終えてステップ7に進む。人のレビュアーはいつ返すか分からないので、待たない。

## 準備

引数がない場合はPR番号を聞く。PRのブランチに切り替わっていない場合は最初に切り替える。

以下を**並列**で実行し、以降のラウンドで使い回す:

```bash
gh repo view --json nameWithOwner --jq '.nameWithOwner'
gh api user --jq '.login'
```

続けて、1つ目の結果を `REPO` として、Copilot がレビューに付いているかを確かめる。`copilot-pull-request-reviewer` で始まるものがあれば付いている:

```bash
gh api "repos/$REPO/pulls/<PR番号>/reviews" --jq '[.[].user.login] | unique'
```

ラウンドの数はここから数える。**上限は5ラウンド**。Copilot は直した箇所の周辺に新しい細かい指摘を出し続けることがあり、上限がないと終わらない。

## ステップ1: 未解決スレッドの取得

```bash
ruby ~/.claude/skills/resolving-pr-reviews/scripts/fetch_pr_comments.rb "$REPO" <PR番号>
```

**最後のコメントが自分のスレッドは除外する。** 前のラウンドで返信済みで、人のレビュアーの resolve 待ちになっているもの。レビュアーが再度返信していれば最後のコメントは相手のものになるので、自然に対象に戻る。

除外したあとで0件なら、ステップ7へ進む。

## ステップ2: 仕分け

各スレッドを次の3つに分け、`TodoWrite` に1スレッド1項目で積む。コンパクトを挟むと、どれを直さないと決めたかが消えるため。

| 仕分け | 基準 |
|---|---|
| 直す | 指摘が正しく、直し方が1つに決まる |
| 直さない | 誤読・既存の設計判断と衝突・PR の範囲外。理由を1文で書けるもの |
| ユーザーに聞く | 意図が読み取れない、仕様の判断が要る、直し方が複数あって優劣がつかない |

「ユーザーに聞く」はここでは止めず、ステップ4の提示でまとめて聞く。答えが出たものはステップ3に戻って直す。

影響範囲が広い指摘は Agent ツール（subagent_type: Explore）で調べてから仕分ける。

前のラウンドで「直さない」と決めた指摘と同じ内容が出てきたら、同じ理由で「直さない」に入れる。判断を変えない。

## ステップ3: 実装とコミット

「直す」のスレッドをまとめて実装し、変更したファイルに関係するテストや lint を実行する。

`/git-commit` でコミットを作成する。`/git-commit` のユーザー確認はステップ4に回し、ここでは取らない。

fixup は作らない。squash には force push が要り、ラウンドごとに履歴を書き換えると、返信に貼ったコミットのリンクが切れるため。

## ステップ4: push の承認

以下をまとめて提示し、承認を得る。**自動で push しない。**

```
## ラウンド 2 / 最大5

### 直した（3件）
[1] app/models/foo.rb:L42 — nil のときの分岐を追加（abc1234）
[2] ...

### 直さない（1件）
[4] app/services/bar.rb:L10 — 呼び出し元で検証済みのため

### 判断してほしい（1件）
[5] app/models/baz.rb:L7 — 〈何を決めてほしいか〉

### コミット
abc1234 fix: ...（メッセージ全文）

### 整理したコメント（/git-commit のステップ3）
app/models/foo.rb:L40 — 「nil チェックを追加」を削除
```

ユーザーが番号で修正を依頼した場合（例: `4 も直して`）は、ステップ3に戻ってから再度ここで確認する。

## ステップ5: push → 返信 → resolve

1. push する前に現在時刻を記録する。ステップ6の待機の起点になる:

   ```bash
   date -u +%Y-%m-%dT%H:%M:%SZ
   ```

2. `git push` を実行する。

3. 各スレッドに返信する。`comment_id` にはスレッドの最初のコメントの `database_id` を使う:

   ```bash
   gh api repos/{owner}/{repo}/pulls/{pr_number}/comments/{comment_id}/replies -f body="返信本文"
   ```

   コミットURLを含める場合は、`gh api` でGitHub上にコミットが存在することを確認してから返信する（リンク切れ防止）。

   **返信テンプレート:**

   - 直した: `こちら対応しました！` + `[<コミットメッセージの1行目>](<コミットのURL>)`
   - 直さない: 直さない理由を1〜2文で書く。レビュアーが読んで納得できるよう、根拠（既存の設計判断、呼び出し元のコード位置など）を添える

   返信文は `humanizer-ja` スキルを読み込み、その基準で見直してから投稿する。

4. resolve する（スレッドの最初のコメントの `author_type` で判定）:
   - `Bot` → 返信後に resolve する（GraphQL mutation `resolveReviewThread` を `thread_id` で実行）。「直さない」も resolve する。残すと次のラウンドで同じスレッドを拾い直すため
   - `User` → 返信のみ。resolve はレビュアーが行う

## ステップ6: Copilot の再レビューを待つ

`--once` のとき、または PR に Copilot のレビューが付いていないときはスキップして、ステップ7へ進む。

ラウンドが上限に達していたら、再レビューを依頼せずにステップ7へ進む。

1. 再レビューを依頼する:

   ```bash
   gh pr edit <PR番号> --add-reviewer @copilot
   ```

2. 待機スクリプトを Bash の `run_in_background: true` で起動する。第3引数はステップ5-1で記録した時刻:

   ```bash
   ruby ~/.claude/skills/resolving-pr-reviews/scripts/wait_for_copilot_review.rb "$REPO" <PR番号> <push前の時刻> 1200
   ```

   終了すると通知が届くので、`sleep` やポーリングを自分で繰り返さない。

   - exit 0: レビューが届いた。ラウンドを1つ進めてステップ1に戻る
   - exit 2: 20分待っても届かなかった。ステップ7へ進み、再レビューが届いていないことを伝える
   - それ以外: `gh api` が失敗した。エラー内容を添えてステップ7へ進む

## ステップ7: 結果報告

```
## 対応結果（3ラウンド）

終了理由: Copilot の新しい指摘なし

### 直した（5件）
[1] path/to/file.rb:L42 — XXXを修正（ラウンド1）
...

### 直さない（2件）
[4] path/to/file.rb:L10 — 理由（ラウンド1）
...

### レビュアー待ち（人の指摘・返信済み）
[6] path/to/file.rb:L88 — @reviewer
```

終了理由は次のいずれか: 新しい指摘なし / `--once` / 上限の5ラウンドに到達 / 再レビューがタイムアウト / 待機中の API エラー / Copilot のレビューが付いていない。

## 注意事項

- スレッドの意図が不明確な場合は推測せずユーザーに確認する
- 人のレビュアーの指摘を「直さない」とする場合も、返信で理由を伝える。黙って残さない
