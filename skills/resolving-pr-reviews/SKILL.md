# resolving-pr-reviews

依存: `gh` CLI（認証済み）、`ruby`、`jq`

```text
resolving-pr-reviews 123         # 指摘がなくなるまで繰り返す
resolving-pr-reviews 123 --once  # 1ラウンドで終える
```

## 全体の流れ

```text
1. 未解決スレッドを取る
   `-> 0件なら 7. 結果を報告する
2. 仕分ける（直す / 直さない / 質問 / ユーザーに聞く）
3. 実装してコミットする
4. 判断が要る指摘をユーザーに聞く（「ユーザーに聞く」があるときだけ）
5. push して Copilot に再レビューを頼み、返信して resolve する
6. Copilot の再レビューが届くまで待つ
   `-> 1. に戻る
7. 結果を報告する
8. 新しい指摘を待つ（PR が開いているあいだ）
   `-> 届いたら 1. に戻る
```

push の承認は取らない。直したコミットは、draft でも ready でも、自分の判断で push する。
ユーザーに止めて確認を取るのは、ステップ2で「ユーザーに聞く」に仕分けた指摘があったときだけ。

draft か ready かで、直し方と返信が変わる:

| PR | 直し方 | 返信に貼るもの |
|---|---|---|
| draft | 直したい箇所を入れたコミットに fixup して、履歴を整えたまま force push | 修正後のコードのパーマリンク |
| ready | 新しいコミットを積む | コミットのリンク |

draft の間は、レビュー前の履歴を整えておく方が、後で読む人に分かりやすい。ready になった後はレビュアーが差分を追っているので、履歴を書き換えずに積む。

再レビューの依頼は、`--once` のときも含めて push のたびに出す。待つのは、`--once` でなく、依頼が通ったときだけ。依頼が通らなければ、ステップ5で終えてステップ7に進む。人のレビュアーはいつ返すか分からないので、待たない。

## dev-flow.md があるとき

`running-dev-flow` から呼ばれると、worktree の git dir に dev-flow.md がある。この skill は、その手順8にあたる。

```bash
"$(git rev-parse --absolute-git-dir)/dev-flow.md"
```

dev-flow.md の Stop hook は、状態が `作業中` で未チェックの手順が残っていると、ターンを終わらせない。そのため、ファイルがあれば次のようにする:

- ユーザーに聞くとき（ステップ4）は、状態が `作業中` なら `ユーザー待ち` に書き換えてから止まる。返事が来ると hook が `作業中` に戻す
- ステップ7で報告したら、手順8にチェックを付けて状態を `完了` にしてから、ステップ8の見張りを始める

## 準備

引数がない場合はPR番号を聞く。PRのブランチに切り替わっていない場合は最初に切り替える。

以下を**並列**で実行し、以降のラウンドで使い回す:

```bash
gh repo view --json nameWithOwner --jq '.nameWithOwner'
gh api user --jq '.login'
gh pr view <PR番号> --json isDraft --jq '.isDraft'
```

3つ目が `true` なら draft。ラウンドごとに見直す。途中で ready にされることがあるため。1つ目の結果を `REPO` として使う。

Copilot にレビューを頼んであって、まだ届いていなければ、先に届くのを待つ。PR を出した直後に呼ばれると、Copilot のレビューが届く前にステップ1で0件になり、「新しい指摘なし」で終わってしまうため。

```bash
gh pr view <PR番号> --json reviewRequests,createdAt \
  --jq '[(.reviewRequests[] | select((.login // "") | test("copilot"; "i"))), .createdAt]'
```

Copilot が依頼中に残っていれば、出てきた `createdAt` を起点にしてステップ6の待機スクリプトを流し、届いてからステップ1に進む。待つあいだに見るものもステップ6と同じ。

ラウンドの数はここから数える。上限は設けず、新しい指摘がなくなるまで回す。前のラウンドで「直さない」と決めた指摘と同じものは、同じ理由で「直さない」にするので、同じ指摘で回り続けることはない。

## ステップ1: 未解決スレッドの取得

```bash
ruby <skill のディレクトリ>/scripts/fetch_pr_comments.rb "$REPO" <PR番号>
```

**最後のコメントが自分のスレッドは除外する。** 前のラウンドで返信済みで、人のレビュアーの resolve 待ちになっているもの。レビュアーが再度返信していれば最後のコメントは相手のものになるので、自然に対象に戻る。

自分のアカウントで AI が付けた指摘は、他人の指摘と同じく対象にする。本文に `🤖` を含み、スレッドの最初のコメントで、まだ誰も返信していないもの。自分の 🤖 付きのレビューも `reviews` に入る。手で書いた（`🤖` のない）自分のコメントは、何件目でも対象にしない。

| スレッドのコメント | 対象か |
|---|---|
| 1. 自分の AI（🤖） | 対象 |
| 1. 自分の AI（🤖）→ 2. 自分の AI の返信（🤖） | 除く |
| 1. 自分の AI（🤖）→ 2. 自分（🤖 なし） | 除く |
| 1. 他人（🤖 の有無は問わない） | 対象 |
| 1. 他人 → 2. 自分の AI の返信（🤖） | 除く |
| 1. 他人 → 2. 自分の AI の返信（🤖）→ 3. 他人 | 対象 |
| 1. 自分（🤖 なし） | 除く |

除外したあとで0件なら、ステップ7へ進む。

## ステップ2: 仕分け

各スレッドを次の4つに分け、セッションの todo に1スレッド1項目で積む。コンパクトを挟むと、どれを直さないと決めたかが消えるため。

| 仕分け | 基準 |
|---|---|
| 直す | 指摘が正しく、直し方が1つに決まる |
| 直さない | 誤読・既存の設計判断と衝突・PR の範囲外。理由を1文で書けるもの |
| 質問 | 直すことを求めず、何かを尋ねている。コードや PR の中身で答えられるもの |
| ユーザーに聞く | 意図が読み取れない、仕様の判断が要る、直し方が複数あって優劣がつかない |

「ユーザーに聞く」はここでは止めず、ステップ4でまとめて聞く。答えが出たものはステップ3に戻って直す。

質問には必ず答える。答えるときは、根拠のコードの位置やコミットを添える。コードや PR から答えられない質問は「ユーザーに聞く」に入れる。答えを調べた結果、直したほうがよいと分かったら「直す」に入れる。

影響範囲が広い指摘は、読むだけのサブエージェントに呼び出し元や同じ書き方の箇所を探させてから仕分ける。探すだけで、直すかの判断は自分でするので、軽いモデルでよい。サブエージェントを使えないときは自分で探す。

前のラウンドで「直さない」と決めた指摘と同じ内容が出てきたら、同じ理由で「直さない」に入れる。判断を変えない。

## ステップ3: 実装とコミット

「直す」のスレッドをまとめて実装し、変更したファイルに関係するテストや lint を実行する。

**ready の PR:** `committing-git-changes` で新しいコミットを作成する。直したスレッドごとに最初のコメントの URL（ステップ1で取った `url`）を渡し、「なぜ必要なのか？」の先頭に置いてもらう。1件なら `[レビューコメント](<URL>) の対応です`、2件以上なら「以下のレビューコメントの対応です」の下に URL を箇条書きで並べる。`committing-git-changes` のユーザー確認は取らない。会社・個人の情報が見つかったときだけ、そこで止まる。

**draft の PR:** 直した箇所を入れたコミットを `git log` と `git blame` で探し、そのコミットに fixup して並べ直す。

```bash
git commit --fixup=<直したい箇所を入れたコミット>
GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <ベースブランチ>
```

`<ベースブランチ>` は、`<skill のディレクトリ>/../creating-pull-requests/scripts/base-branch.sh` が出すブランチにする。

コミットメッセージは変えないので、`committing-git-changes` は通さない。直しが元のコミットの説明と合わなくなるときだけ、そのコミットのメッセージも直す。

## ステップ4: ユーザーに聞く

「ユーザーに聞く」がなければ、止まらずにステップ5に進む。

あれば、その指摘に関係しない直しは先にステップ5で push して返信する。そのあと、聞くものだけを次の形で出して止まり、答えを待つ。

```text
## ラウンド 2

### 判断してほしい（1件）
[5] app/models/baz.rb:L7 — 〈何を決めてほしいか〉
```

答えが出たら、ステップ3に戻って直し、そのままステップ5で push する。

## ステップ5: push → 返信 → resolve

1. push する前に現在時刻を記録する。ステップ6の待機の起点になる:

   ```bash
   date -u +%Y-%m-%dT%H:%M:%SZ
   ```

2. push する。ready の PR は `git push`、draft の PR は履歴を書き換えたので `git push --force-with-lease`。PR がスタックの中にあり、上の層があるときは、`stacking-pull-requests` の 3 で上の層を載せ直してから、まとめて push する。git-rewrite-guard に履歴の書き換えを止められたら、fixup をやめて新しいコミットを積み、`git push` する。

3. Copilot に再レビューを依頼する。前に Copilot のレビューが付いていなくても依頼する:

   ```bash
   gh pr edit <PR番号> --add-reviewer @copilot
   ```

   失敗したら、そのリポジトリでは Copilot のコードレビューが使えない。以降のラウンドでは依頼せず、ステップ6も飛ばす。

4. 各スレッドに返信する。`comment_id` にはスレッドの最初のコメントの `database_id` を使う:

   ```bash
   gh api repos/{owner}/{repo}/pulls/{pr_number}/comments/{comment_id}/replies -f body="返信本文"
   ```

   URL を含める場合は、`gh api` でGitHub上にコミットが存在することを確認してから返信する（リンク切れ防止）。

   返信の中身・リンクの作り方・footer は `<skill のディレクトリ>/references/replies.md` に従う。返信文は `yomiyasu`（英語なら `humanizer`）で推敲してから投稿する。

5. resolve する（スレッドの最初のコメントの `author_type` で判定）:
   - `Bot` → 返信後に resolve する（GraphQL mutation `resolveReviewThread` を `thread_id` で実行）。「直さない」も resolve する。残すと次のラウンドで同じスレッドを拾い直すため
   - `User` → 返信のみ。resolve はレビュアーが行う

## ステップ6: Copilot の再レビューを待つ

`--once` のとき、またはステップ5-3の依頼が通らなかったときはスキップして、ステップ7へ進む。

同梱のスクリプトを `hc run --bg --name copilot-wait <skill のディレクトリ>/scripts/wait-copilot.sh "$REPO" <PR番号> <since>` で起動する。`since` はステップ5-1で記録した時刻。指摘のないレビューはスレッドを作らないので、スクリプトはスレッドの数ではなく、Copilot のレビューが `since` より後に届いたかで見る。30秒ごとに、10分まで待つ。

`hc wait copilot-wait` で終わるのを待ち、`hc read copilot-wait` で出力を読む。終わったら `hc rm copilot-wait` で消す。`sleep` やポーリングを自分で繰り返さない。

待つあいだに CI の結果も見て、失敗を拾う。

```bash
gh pr checks <PR番号> --json name,state,link --jq '.[] | select(.state == "FAILURE")'
```

落ちたものがあれば原因を調べて直し、ステップ3と同じ方法でコミットしておく。push は、次のラウンドで指摘の直しと一緒にする。Copilot の新しい指摘がなくても、CI の直しが残っていればステップ5から進める。まだ動いている CI は待たない。

- exit 0: レビューが届いた。ラウンドを1つ進めてステップ1に戻る
- exit 2: 10分待っても届かなかった。ステップ7へ進み、再レビューが届いていないことを伝える
- それ以外: `gh` が失敗した。エラー内容を添えてステップ7へ進む

## ステップ7: 結果報告

```text
## 対応結果（3ラウンド）

終了理由: Copilot の新しい指摘なし

### 直した（5件）
[1] path/to/file.rb:L42 — XXXを修正（ラウンド1）
...

### 直さない（2件）
[4] path/to/file.rb:L10 — 理由（ラウンド1）
...

### 答えた質問（1件）
[5] path/to/file.rb:L20 — 答えの要約（ラウンド1）

### コミット
abc1234 fix: ...（ラウンド1）

### 整理したコメント（committing-git-changes のステップ3）
path/to/file.rb:L40 — 「nil チェックを追加」を削除

### レビュアー待ち（人の指摘・返信済み）
[6] path/to/file.rb:L88 — @reviewer
```

終了理由は次のいずれか: 新しい指摘なし / `--once` / 再レビューがタイムアウト / 待機中の API エラー / Copilot のコードレビューが使えない。

draft の PR で終了理由が「新しい指摘なし」なら、報告の前に ready にする。Copilot の最新のレビューで追加の指摘がなく、レビュアーに見てもらえる状態になったため。

```bash
gh pr ready <PR番号>
```

報告の終了理由の下に「ready にした」と書く。ほかの終了理由では ready にしない。指摘が残っているか、まだ確かめきれていないため。

## ステップ8: 新しい指摘を待つ

報告したら、PR が開いているあいだ新しい指摘と人のレビューを見張る。`--once` のときは見張らない。見張るときは `<skill のディレクトリ>/references/watching.md` を読み、それに従う。dev-flow.md があれば、起動する前に手順8にチェックを付けて状態を `完了` にする（上の「dev-flow.md があるとき」）。

## 注意事項

- 人のレビュアーの指摘を「直さない」とする場合も、返信で理由を伝える。黙って残さない
