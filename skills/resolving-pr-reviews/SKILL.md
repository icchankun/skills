# PRレビュースレッド対応

依存: `gh` CLI（認証済み）、`ruby`

```
/resolving-pr-reviews 123         # 指摘がなくなるまで繰り返す
/resolving-pr-reviews 123 --once  # 1ラウンドで終える
```

## 全体の流れ

```
1. 未解決スレッドを取る
   `-> 0件なら 7. 結果を報告する
2. 仕分ける（直す / 直さない / ユーザーに聞く）
3. 実装してコミットする
4. push の承認を取る（ready の PR のときだけ）
5. push して Copilot に再レビューを頼み、返信して resolve する
6. Copilot の再レビューが届くまで待つ
   `-> 1. に戻る
```

ユーザーに止めて確認を取るのは、ready の PR でのステップ4の push 前と、ステップ2で判断が要る指摘があったときだけ。

draft か ready かで、直し方と返信が変わる:

| PR | 直し方 | 返信に貼るもの | push の承認 |
|---|---|---|---|
| draft | 直したい箇所を入れたコミットに fixup して、履歴を整えたまま force push | 修正後のコードのパーマリンク | 取らない |
| ready | 新しいコミットを積む | コミットのリンク | 取る |

draft の間は、レビュー前の履歴を整えておく方が、後で読む人に分かりやすい。ready になった後はレビュアーが差分を追っているので、履歴を書き換えずに積む。

再レビューの依頼は、`--once` のときも含めて push のたびに出す。待つのは、`--once` でなく、依頼が通ったときだけ。依頼が通らなければ、ステップ5で終えてステップ7に進む。人のレビュアーはいつ返すか分からないので、待たない。

## 準備

引数がない場合はPR番号を聞く。PRのブランチに切り替わっていない場合は最初に切り替える。

以下を**並列**で実行し、以降のラウンドで使い回す:

```bash
gh repo view --json nameWithOwner --jq '.nameWithOwner'
gh api user --jq '.login'
gh pr view <PR番号> --json isDraft --jq '.isDraft'
```

3つ目が `true` なら draft。ラウンドごとに見直す。途中で ready にされることがあるため。1つ目の結果を `REPO` として使う。

Copilot にレビューを頼んであって、まだ届いていなければ、先に届くのを待つ。PR を出した直後に呼ばれると、Copilot のレビューが届く前にステップ1で0件になり、「新しい指摘なし」で終わってしまうため。

```bash
gh pr view <PR番号> --json reviewRequests,createdAt \
  --jq '[(.reviewRequests[] | select((.login // "") | test("copilot"; "i"))), .createdAt]'
```

Copilot が依頼中に残っていれば、出てきた `createdAt` を起点にしてステップ6の待機スクリプトを流し、届いてからステップ1に進む。待つあいだに見るものもステップ6と同じ。

ラウンドの数はここから数える。上限は設けず、新しい指摘がなくなるまで回す。前のラウンドで「直さない」と決めた指摘と同じものは、同じ理由で「直さない」にするので、同じ指摘で回り続けることはない。

## ステップ1: 未解決スレッドの取得

```bash
ruby ~/.claude/skills/resolving-pr-reviews/scripts/fetch_pr_comments.rb "$REPO" <PR番号>
```

**最後のコメントが自分のスレッドは除外する。** 前のラウンドで返信済みで、人のレビュアーの resolve 待ちになっているもの。レビュアーが再度返信していれば最後のコメントは相手のものになるので、自然に対象に戻る。

除外したあとで0件なら、ステップ7へ進む。

## ステップ2: 仕分け

各スレッドを次の3つに分け、`TodoWrite` に1スレッド1項目で積む。コンパクトを挟むと、どれを直さないと決めたかが消えるため。

| 仕分け | 基準 |
|---|---|
| 直す | 指摘が正しく、直し方が1つに決まる |
| 直さない | 誤読・既存の設計判断と衝突・PR の範囲外。理由を1文で書けるもの |
| ユーザーに聞く | 意図が読み取れない、仕様の判断が要る、直し方が複数あって優劣がつかない |

「ユーザーに聞く」はここでは止めず、ステップ4の提示でまとめて聞く。答えが出たものはステップ3に戻って直す。

影響範囲が広い指摘は Agent ツール（subagent_type: Explore、model: haiku）で、呼び出し元や同じ書き方の箇所を探させてから仕分ける。探すだけで、直すかの判断は自分でするため。

前のラウンドで「直さない」と決めた指摘と同じ内容が出てきたら、同じ理由で「直さない」に入れる。判断を変えない。

## ステップ3: 実装とコミット

「直す」のスレッドをまとめて実装し、変更したファイルに関係するテストや lint を実行する。

**ready の PR:** `/committing-git-changes` で新しいコミットを作成する。`/committing-git-changes` のユーザー確認はステップ4に回し、ここでは取らない。

**draft の PR:** 直した箇所を入れたコミットを `git log` と `git blame` で探し、そのコミットに fixup して並べ直す。

```bash
git commit --fixup=<直したい箇所を入れたコミット>
GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <ベースブランチ>
```

コミットメッセージは変えないので、`/committing-git-changes` は通さない。直しが元のコミットの説明と合わなくなるときだけ、そのコミットのメッセージも直す。

## ステップ4: push の承認

ready の PR のときだけ行う。draft の PR ではステップ5に進む。

以下をまとめて提示し、承認を得る。**ready の PR は自動で push しない。**

```
## ラウンド 2

### 直した（3件）
[1] app/models/foo.rb:L42 — nil のときの分岐を追加（abc1234）
[2] ...

### 直さない（1件）
[4] app/services/bar.rb:L10 — 呼び出し元で検証済みのため

### 判断してほしい（1件）
[5] app/models/baz.rb:L7 — 〈何を決めてほしいか〉

### コミット
abc1234 fix: ...（メッセージ全文）

### 整理したコメント（/committing-git-changes のステップ3）
app/models/foo.rb:L40 — 「nil チェックを追加」を削除
```

ユーザーが番号で修正を依頼した場合（例: `4 も直して`）は、ステップ3に戻ってから再度ここで確認する。

## ステップ5: push → 返信 → resolve

1. push する前に現在時刻を記録する。ステップ6の待機の起点になる:

   ```bash
   date -u +%Y-%m-%dT%H:%M:%SZ
   ```

2. push する。ready の PR は `git push`、draft の PR は履歴を書き換えたので `git push --force-with-lease`。PR がスタックの中にあり、上の層があるときは、`stacking-pull-requests` の 3 で上の層を載せ直してから、まとめて push する。

3. Copilot に再レビューを依頼する。前に Copilot のレビューが付いていなくても依頼する:

   ```bash
   gh pr edit <PR番号> --add-reviewer @copilot
   ```

   失敗したら、そのリポジトリでは Copilot のコードレビューが使えない。以降のラウンドでは依頼せず、ステップ6も飛ばす。

4. 各スレッドに返信する。`comment_id` にはスレッドの最初のコメントの `database_id` を使う:

   ```bash
   gh api repos/{owner}/{repo}/pulls/{pr_number}/comments/{comment_id}/replies -f body="返信本文"
   ```

   URL を含める場合は、`gh api` でGitHub上にコミットが存在することを確認してから返信する（リンク切れ防止）。

   **返信テンプレート:**

   - 直した（ready）: `こちら対応しました！` + `[<コミットメッセージの1行目>](<コミットのURL>)` + なぜその直し方にしたかを1文
   - 直した（draft）: `こちら対応しました！` + 修正後のコードのパーマリンク + なぜその直し方にしたかを1文。パーマリンクは push 後の HEAD の SHA で作る（`https://github.com/<REPO>/blob/<SHA>/<パス>#L<開始>-L<終了>`）。fixup で元のコミットの SHA は変わるので、push 前の SHA を使わない
   - 直さない: 直さない理由を1〜2文で書く。レビュアーが読んで納得できるよう、根拠（既存の設計判断、呼び出し元のコード位置など）を添える

   返信文は `reviewing-writing` スキルで見直してから投稿する。

4. resolve する（スレッドの最初のコメントの `author_type` で判定）:
   - `Bot` → 返信後に resolve する（GraphQL mutation `resolveReviewThread` を `thread_id` で実行）。「直さない」も resolve する。残すと次のラウンドで同じスレッドを拾い直すため
   - `User` → 返信のみ。resolve はレビュアーが行う

## ステップ6: Copilot の再レビューを待つ

`--once` のとき、またはステップ5-3の依頼が通らなかったときはスキップして、ステップ7へ進む。

待機スクリプトを Bash の `run_in_background: true` で起動する。第3引数はステップ5-1で記録した時刻:

```bash
ruby ~/.claude/skills/resolving-pr-reviews/scripts/wait_for_copilot_review.rb "$REPO" <PR番号> <push前の時刻> 600
```

終了すると通知が届くので、`sleep` やポーリングを自分で繰り返さない。

待つあいだに CI の結果も見て、失敗を拾う。

```bash
gh pr checks <PR番号> --json name,state,link --jq '.[] | select(.state == "FAILURE")'
```

落ちたものがあれば原因を調べて直し、ステップ3と同じ方法でコミットしておく。push は、次のラウンドで指摘の直しと一緒にする。Copilot の新しい指摘がなくても、CI の直しが残っていればステップ4から進める。まだ動いている CI は待たない。

- exit 0: レビューが届いた。ラウンドを1つ進めてステップ1に戻る
- exit 2: 10分待っても届かなかった。ステップ7へ進み、再レビューが届いていないことを伝える
- それ以外: `gh api` が失敗した。エラー内容を添えてステップ7へ進む

## ステップ7: 結果報告

```
## 対応結果（3ラウンド）

終了理由: Copilot の新しい指摘なし

### 直した（5件）
[1] path/to/file.rb:L42 — XXXを修正（ラウンド1）
...

### 直さない（2件）
[4] path/to/file.rb:L10 — 理由（ラウンド1）
...

### レビュアー待ち（人の指摘・返信済み）
[6] path/to/file.rb:L88 — @reviewer
```

終了理由は次のいずれか: 新しい指摘なし / `--once` / 再レビューがタイムアウト / 待機中の API エラー / Copilot のコードレビューが使えない。

draft の PR で終了理由が「新しい指摘なし」なら、報告の前に ready にする。Copilot の最新のレビューで追加の指摘がなく、レビュアーに見てもらえる状態になったため。

```bash
gh pr ready <PR番号>
```

報告の終了理由の下に「ready にした」と書く。ほかの終了理由では ready にしない。指摘が残っているか、まだ確かめきれていないため。

## 注意事項

- スレッドの意図が不明確な場合は推測せずユーザーに確認する
- 人のレビュアーの指摘を「直さない」とする場合も、返信で理由を伝える。黙って残さない
