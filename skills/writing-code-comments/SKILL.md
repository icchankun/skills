# writing-code-comments

コメントに書くのは、コードを読んでも分からないことだけにする。なぜそうしたか、制約、外部の仕様、ハマりどころなどがそれにあたる。迷ったら書かない。AI はコメントを書きすぎるので、書いたものは疑ってかかる。

## 書かないもの

| 型 | 例 | 代わりにどうするか |
|---|---|---|
| コードの言い換え | `# 単価 x 数量の総和を返す` の下に `items.sum { _1.unit_price * _1.quantity }` | 消す。残すなら「なぜ」を書く（`# 丸め誤差を避けるため BigDecimal にする`） |
| 変更の経緯・作業メモ | `# ヘルメットが必須になった`、`# 〜を修正`、`# 以前は〜だった`、`# 新しく追加` | 消して、コミットメッセージか PR に書く。今の仕様が過去の仕様に縛られているときだけ残す |
| 呼び出し元の説明 | `def cancel_payment` の上の `# 退会画面のコントローラから呼ばれる` | 消す。必要なら、呼ぶ側のコードに書く |
| 同じ説明を2か所 | `after_destroy :cancel_payment` と `def cancel_payment` の両方に「退会したら課金を取り消す」 | 片方だけにする。仕様なら、テストの `describe` や `it` に書く |
| 置き場所の責務から外れた話 | モデルの定数の上に、編集画面での出し分けの説明 | 消す。画面の都合は画面のコードに書く |
| 名前から分かることを繰り返す docstring | `# @param user ユーザー` | 消す |
| 区切りや飾りだけの行、中身のない「重要:」「注意:」 | `# ====== Helpers ======` | 消す |
| `ponytail:` の目印 | `# ponytail: global lock, per-account locks if throughput matters` | 書かない。手を抜いた箇所の限界と直し方は、コミットメッセージか PR に書く |

ponytail の skill は、わざと簡単にした箇所へ `ponytail:` のコメントを付けるよう言う。この skill はそれより優先する。

## 書くときの決まり

- 説明するコードの直前に置く。メソッドの中の1つの処理の説明を、メソッドの上に書かない。メソッド全体の説明に見えるため。
- コードにある名前を使う。コードが `:single_coil` なら、コメントも「シングルコイル」ではなく `single_coil` と書く。コードにない言葉（「ハムバッカー」）で説明しない。
- 読んだ人が次に持つ疑問に答える。`# このクラスは画面から使われていない` だけだと「では消してよいのか」が残る。`# 過去に登録されたデータを読むため、画面からは使わないがモデルとテーブルを残している` まで書く。
- 1つの意味にしか読めない文にする。`# 解約すると仮注文の確定と自動継続を止めるので、仮注文には何もしない` は、何が何を止めるのかが読めない。
- 1行で言えることを複数行にしない。
- `humanizer-ja` の癖（大げさな言葉、念押し、翻訳調）を入れない。

## 書いたあと

足したか書き換えたコメントを、上の表と決まりに当てて見直す。会話の外に残る文なので、残したものは `reviewing-writing` で見直す。既存のコメントは、頼まれない限り直さない。
