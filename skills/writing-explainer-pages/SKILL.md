# writing-explainer-pages

説明の資料を、図を中心にした1枚の HTML のページにする。読み手は、この会話を持っていない人。会話では通じた前提も、ページの中で分かるように書く。

この skill は、3つの skill をいつ・どの順で使うかと、利用者が決めた見せ方の決まりを書く。各 skill の中身は、その SKILL.md に従う。中身をここに写すと、元の skill が更新されたときに食い違うため。

| 何を | 従う skill |
|---|---|
| 文（見出し・説明・表の中の文） | `yomiyasu` |
| 図と表の選び方・描き方・render の確認 | `visual-explainer` |
| 見た目（色・余白・文字・AI が作ったように見えるところ） | `unslop` |

## 1. 読む

作る前に、`yomiyasu`、`visual-explainer`、`unslop` の SKILL.md を読む。artifact にするときは、Artifact のツールの説明に従い `artifact-design` も読む。書いたあとで3つに合わせ直すと、ページ全体の書き直しになるため。

## 2. 見出しの構成を決めて見せる

- 見出しは、読み手が持つ問いの形にする（例: 「RTMP とは何か」「なぜライブ配信では RTMP を使うのか」）。問いの形だと、読み手は目次を見ただけで、自分の疑問の答えがどこにあるかを探せる。
- 見出しは、読み手が問いを持つ順に並べる。前の章の答えが、次の章の問いの前提になるようにする。順が逆だと、読み手は先の章を読まないと今の章が分からない。
- ページの題は、内容に合う2〜4語の名前にする。題はタブやギャラリーに出るので、長い説明文だと切れて読めない。
- 構成（題と見出しの一覧）を利用者に見せ、OK が出てから書く。構成が違うと本文をすべて書き直すことになるので、いちばん安い段階で確かめる。利用者が構成を先に渡したときは、それに従う。

## 3. 書く

### 文と図の分け方
- 文を減らす。図や表に入れられる内容は、図や表に入れる。文は図の説明と、図にできない理由づけだけにする。読み手は文より先に図を見て、図で分からない所だけ文を読むため。
- 補足はトグル（`<details>` など）に隠さず、本文の流れの中に書く。トグルは開かれないことが多く、流し読みする読み手に届かない。補足が長すぎて本文に入らないなら、その補足は図にするか削る。
- 要らない補助のラベルを付けない（例: 見出しの上の小さな英字、「Step 1」の飾り、図の横の説明の札、「ポイント」の見出し）。図や表の形と並びに意味を語らせる。ラベルは情報を足さずに目を止める所を増やし、AI が作ったページに見える原因にもなる。

### 目次
- ページの最初（題と導入の文のすぐあと）に、各章へリンクする目次を置く。問いの形の見出しが並ぶので、目次がそのまま「このページで分かること」の一覧になる。

### 色
- 色は `:root` のトークンで決め、ダークモードの値も書く。色を1か所で変えられ、どちらの表示でも文字が読めるようにするため。
- 強い色は1つの意味にだけ使い、その意味をページ全体で変えない（例: 赤は RTMP の経路だけ）。読み手は色を手がかりに図の中の経路を追う。ほかの所にも同じ色を使うと、その手がかりが使えなくなる。
- ほかの強調は、色のない太い枠線と濃い線で表す。強調を色に頼らなければ、強い色の意味を守れる。

### 図（SVG）
- SVG は横にスクロールする枠に入れ、`min-width` を viewBox の幅にそろえる。幅に合わせて縮めると、スマートフォンで図の中の文字が読めない大きさになる。スクロールさせれば、文字の大きさを保てる。
- 図の中の文字は 12.5px 以上にする。visual-explainer の render は 12px 未満の文字を ✗ にするので、少し余裕をとる。
- 文字を線や枠と重ねず、文字と枠のあいだに余白をとる。重なると読めず、どの箱の文字かも分からなくなる。

## 4. 確かめる

1. 本文に `yomiyasu` の run と verify を通す。ページの本文を抜き出したファイルを渡す。HTML のタグのまま渡すと、検査がタグを文として読んでしまう。
2. `visual-explainer` の render を実行し、出た ✗ をすべて直す。
3. 2の sheet を一度見て、3章の決まり（ラベル・トグル・色・文字の大きさ・重なり）が守られているかを確かめる。render が見つけない決まりもあるため。

## 5. 公開する

- artifact は Artifact のツールで公開する。
- Notion の HTML ブロックにするときは、書き込みを writing-notion-docs の手順で行う。書く場所と HTML を見せ、OK が出てから書き込む。
- 直すときは、ページ全体を書き直さず、直す所だけを小さく直す。全体を書き直すと、利用者が確かめ済みの所まで変わってしまう。
- 直す前の版を、別の名前のファイルに残す（例: `name.v5.html`）。直した結果が悪かったときに戻せるようにするため。
- 直したあとは4章をもう一度通し、同じ file_path で公開する。file_path を変えると URL が変わり、利用者が共有したリンクが古い版を指したままになる。

## 6. コメントに応える

- 利用者がページにコメントを付けたら、そのコメントの場所に説明を書き足す。コメントは、そこで読み手がつまずいたという印なので、別の場所や会話の中で答えても、次の読み手には届かない。トグルにせず本文に書く。
- 書き足したら、どこに何を書き足したかを報告する。利用者がページを開き直さなくても確かめられるようにするため。
- 説明を足すたびに、ほかに削れる文がないかを見る。足すだけだと、ページが文の多い状態に戻る。
