# /github-pr スキル

gitのコミット情報の解析からdraft PR作成まで一気通貫で行う。
PRタイトルとdescriptionをコミットメッセージから自動生成することで、手作業でのコピペや整形を不要にする。

## 手順

### ステップ1: ベースブランチを決める

PRのマージ先（ベースブランチ）を次の順で決める。以降の `<base>` はここで決めたブランチを指す:

1. 引数で指定されたブランチ
2. `git config branch.<現在のブランチ>.gh-merge-base` の値（`/git-branch` が作成元を記録している）
3. リポジトリのデフォルトブランチ

```bash
git config "branch.$(git branch --show-current).gh-merge-base"
gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'
```

`gh pr create` も `--base` がなければ同じ順で決めるが、確認と rebase に使うため、ここで明示的に決めておく

### ステップ2: 現状を把握する

以下を**並列**で実行し、PRに含まれるコミットと変更内容を把握する:

```bash
git branch --show-current
git log --oneline <base>..HEAD
git log <base>..HEAD --reverse --format='%B---COMMIT_SEPARATOR---'
git diff <base>..HEAD --name-only
```

**中断条件** — 以下のいずれかに該当する場合は処理を止め、理由を伝える:

- 現ブランチがベースブランチまたはデフォルトブランチである — 保護ブランチへの直接pushが発生するため
- ベースブランチからのコミットがない — PRに含める変更がないため

### ステップ3: PRタイトルを組み立てる

PRタイトルは `[チケットID][サービス名] サマリー` の形式にする。

#### チケットIDの抽出

ブランチ名からチケットIDパターンを探す。代表的なパターン:

| パターン | 例 | 抽出結果 |
|----------|------|----------|
| `[A-Z]+-\d+`（JIRA / Notion 等） | `feat/PROJ-123-add-auth` | `[PROJ-123]` |
| `#\d+`（GitHub Issues） | `fix/#42-login-error` | `[#42]` |
| 該当なし | `fix/login-error` | 省略 |

#### サービス名の推定

変更ファイルのパスやクラスの名前空間から、この変更がどの機能領域に属するかを推定する:

1. `git diff <base>..HEAD --name-only` の `app/` 配下のパスを見る
2. モデル・コントローラ等のディレクトリ名（名前空間）の出現頻度を集計する
3. 最も多い名前空間からチームが普段PRタイトルで使うサービス名を判断する

複数領域にまたがる場合や汎用的な名前空間しかない場合は省略する。

#### サマリーの抽出

最初のコミット（`--reverse` で最も古いもの）の1行目から、Conventional Commitsのprefix（`feat:`, `fix:`, `refactor:` 等）を除いた部分をサマリーとする。

#### 組み立てパターン

要素の有無に応じて自然に組み立てる:

```
[PROJ-123][認証] ログイン時のトークン検証を追加
[PROJ-123] 依存パッケージのアップデート
[認証] ログイン時のエラーハンドリングを修正
ログイン時のエラーハンドリングを修正
```

### ステップ4: PR descriptionを作成する

プロジェクトに `.github/PULL_REQUEST_TEMPLATE.md` がある場合はそれを読み込み、ベースにする。

コミットメッセージの本文（3行目以降）を、テンプレートの冒頭コメント・ヘッダ行の直後・最初の `##` 見出しの手前に挿入する。`## 動作確認` は後述の手順に従って埋め、それ以外のセクション（`## チェックリスト` 等）はそのまま残す。

**挿入イメージ（テンプレートがある場合）:**

```markdown
※リリースフローについては [deploy.md](...) を確認してください。

[コミットメッセージの3行目以降をここに挿入]

## 動作確認

...
```

テンプレートがない場合は、コミットメッセージの本文（3行目以降）をそのまま description とする。

**複数コミットがある場合:**

- 「なぜ必要なのか？」に相当する背景・課題の記述は、各コミットの内容が自然につながるよう文章としてまとめ直す
- 「変更内容」に相当する箇条書きも、コミット単位ではなく変更の意味単位でまとめる

#### 動作確認の記載

`## 動作確認` には、レビュアーが手動で画面上から確かめるべき項目をチェックリスト形式で記載する。

自動テストで既に検証されている内容は書かない。CIの結果で分かることを人手で繰り返す必要はなく、書くほどチェックリスト全体の密度が下がるため。

変更差分から画面上に現れる挙動を読み取り、「どこで何をすると、どうなるか」が分かる粒度で書く:

```markdown
## 動作確認

- [ ] ログイン画面でメールアドレスを空のまま送信すると、入力欄の下にエラーメッセージが表示される
- [ ] 正しい認証情報でログインすると、ダッシュボードへ遷移する
- [ ] セッション切れの状態で操作すると、ログイン画面へ戻される
```

テンプレートに `## 動作確認` がある場合はその配下に挿入し、ない場合は変更内容の後にセクションごと追加する。

画面に現れる変更がない場合（内部リファクタ、CI設定の変更等）は、確認項目を無理に作らず「UI上の変更なし」と1行で記載する。

#### 文章の見直し

複数コミットをまとめ直した文章や動作確認の項目は、`humanizer-ja` スキルを読み込み、その基準で見直してから提示する。コミットメッセージをそのまま使った部分は `/git-commit` で見直し済みなので、手を入れない。

### ステップ5: ユーザーに確認する

以下を提示して承認を得る:

- **PRタイトル**
- **PR description**（全文）
- **ベースブランチ**: `<base>`（ステップ1でどの方法で決めたかを添える）

ユーザーがタイトルやdescriptionの修正を求めた場合は反映してから進む。

### ステップ6: rebase & push & PR作成

承認後、以下を順に実行する:

1. ベースブランチの最新をrebase:
   ```bash
   git pull --rebase origin <base>
   ```
   コンフリクトが発生した場合はユーザーに伝えて処理を中断する。自動でコンフリクト解消は行わない。

2. リモートにpush（未pushの場合）:
   ```bash
   git push -u origin HEAD
   ```

3. draft PRを作成:
   ```bash
   gh pr create --draft --base <base> --title "タイトル" --body "$(cat <<'EOF'
   description全文
   EOF
   )"
   ```

4. 作成されたPRのURLをユーザーに表示する。

## 禁止事項

- ユーザーの承認なしに `git push` や `gh pr create` を実行しない — 共有リポジトリへの操作は確認が必須
- ベースブランチやデフォルトブランチの上では絶対にpushしない — 保護ブランチへの直接pushは事故のもと
- コミットの作成・変更はしない — それは `/git-commit` の役割
