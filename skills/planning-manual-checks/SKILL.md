# planning-manual-checks

レビュアーがブラウザを触って確かめる項目と、スクショと動画のどちらを撮るかを、撮影と PR より先に決める。動画はこの項目に沿って撮り、PR にも同じ項目を載せる。

## 項目にする基準

項目にするのは、自動テストでは確かめにくく、ブラウザで実際に確かめるべきものだけにする。迷ったら次の順で決める。

```text
項目の候補
|-> 1. 自動テスト（system spec など）で、すでに確かめているか
|   `-> はい: 書かない
|-> 2. 自動テストを書けば確かめられるか
|   `-> はい: 「テストを足すもの」に書き、running-dev-flow の手順 2 に戻してテストを足す
`-> 3. 見た目・操作感・ブラウザの違いなど、人が見ないと判断できないか
    `-> はい: 項目にする
```

- 1: CI で分かることを人手で繰り返すと、項目全体の密度が下がるため
- 2: テストのほうが毎回確かめられるため

## 1. 項目を書く

差分から画面上に現れる挙動を読み取り、上の基準で選んだものを「どこで何をすると、どうなるか」が分かる粒度で書く。

```markdown
- [ ] 画面の幅を狭めても、一覧の表が横にはみ出さず、横にスクロールして読める
- [ ] 長い記事のタイトルが2行で折り返され、右の編集ボタンと重ならない
- [ ] Safari で日付を選ぶと、入力欄に選んだ日付が入る
```

画面に現れる変更がない場合（内部リファクタ、CI設定の変更等）は、項目を作らず「UI上の変更なし」と1行で書き、2 は飛ばす。3 の撮るものは「なし」になる。

## 2. 2体で確かめる

次の2体のサブエージェントを同時に動かす。差分と観点を照らし合わせるだけなので、標準のモデルでよい。役割を反対向きにするのは、同じ役割だと同じ見落としをしやすいため。サブエージェントを使えないときは、削る側と足す側を順に自分で行う。

| 役割 | すること | 渡すもの |
|---|---|---|
| 削る側 | 項目ごとに、上の基準の 1（もう自動テストで確かめている）か 2（テストを書けば確かめられる）に当たるか、画面では見えないものを挙げる。1 には、根拠になるテストのファイルと行を添えさせる | 1 の項目、差分、変更に関係するテスト |
| 足す側 | ブラウザで実際に触らないと分からないのに、項目にないものを挙げる。`references/viewpoints.md` の観点を順に当てて探す。どの画面で何をするかが書かれておらず、その通りに操作できない項目も挙げる | 1 の項目、差分、`references/viewpoints.md` |

2体の結果を driver が突き合わせて直す。

- 削る側が 1 に当たるとしたものは、テストの場所を確かめてから削る。場所を示せないものは削らない。「たぶんテストされている」で確かめるべき項目が消えるのを防ぐため。
- 削る側が 2 に当たるとしたものは、テストを書けるかを driver が判断する。書けるなら「テストを足すもの」に移す。
- 足す側が挙げたものは、上の基準に当てはめてから足す。観点に当たっていても、今回の差分に関係しないものは足さない。

## 3. 撮るものを決める

2 で直した項目と差分から、スクショ（capturing-screens）と動画（recording-manual-checks）のどちらを撮るかを決める。2つの問いを別々に答え、その組み合わせで決める。どちらか一方で足りるのに両方を撮ると、撮る時間と PR を読む時間がむだにかかるため。

```text
差分と項目
|-> Q0. 画面に現れる変更があるか
|   `-> いいえ: なし
|-> Q1. URL を開いた1枚の静止画で、変更前と変更後の違いが伝わるか
|   `-> はい: スクショを撮る
`-> Q2. 項目に、操作して結果を確かめるものがあるか
    `-> はい: 動画を撮る
```

- Q1: レイアウト・色・余白・文言・アイコン・表示する項目の追加・新しい画面など、開けば見える変化。変更前と変更後で同じ画像になるなら「いいえ」にする。同じ画像を並べても違いが伝わらないため。
- Q2: クリック・入力・画面の移動・非同期の更新・アニメーション・キーボードの操作など、操作のあとに結果が出る項目。項目がすべて開けば見えるものなら「いいえ」にする。スクショで足りるため。

| 撮るもの | Q1 | Q2 | 例 |
|---|---|---|---|
| スクショだけ | はい | いいえ | 文言・色・余白の修正、アイコンの差し替え、一覧に列を足す |
| 動画だけ | いいえ | はい | 見た目は同じで振る舞いだけ変わるもの。二重送信の防止、フォーカスの移動、保存したあとの移動先、Turbo の部分的な更新の不具合の修正 |
| 両方 | はい | はい | 新しいフォームやモーダル、見た目と操作の両方が変わる部品 |
| なし | — | — | Q0 が「いいえ」。リファクタ、API やバッチだけの変更、CI の設定、見た目の変わらない依存の更新 |

迷いやすいもの:

- 操作しないと出ない状態の見た目が変わる（エラーメッセージの見た目など）: capturing-screens は URL を開いて撮るだけなので、Q1 は「いいえ」にして動画で見せる。項目の最後で `expect_text` か `spot` でその状態を照らす。
- 新しく作った画面で、操作して確かめるものがない: スクショだけ。変更前はなく、変更後だけを撮る。
- 不具合の修正: 見た目の不具合なら Q1、再現に操作が要る不具合なら Q2 に当てはめる。

## 4. 書く

`reviewing-writing` で見直した項目を、dev-flow.md の「動作確認」の節に書く。テストを足すものがあれば、その下に分けて書く。dev-flow.md がなければ結果として返す。

「動作確認」の節の先頭に、3 で決めた撮るものを `撮るもの: スクショだけ / 動画だけ / 両方 / なし` のどれかで1行書き、理由を添える。running-dev-flow はこの行で撮影の手順を飛ばすかを決める。

```markdown
## 動作確認

撮るもの: 両方（一覧の表の見た目が変わり、横にスクロールする操作がある）

- [ ] 画面の幅を狭めても、一覧の表が横にはみ出さず、横にスクロールして読める

テストを足すもの:
- 保存の失敗時にエラーメッセージが出る（spec/system/posts_spec.rb に足す）
```
