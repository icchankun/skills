# following-repo-conventions

これから実装する内容に近い既存コードを読み、そのリポジトリでの書き方をメモにする。一般論ではなく、このリポジトリの近くのコードを基準にする。

## 1. 調べる場所を決める

依頼の要件から、触りそうな場所を挙げる。

- 足す・変えるクラスと同じディレクトリ、同じ層（モデル・サービス・コントローラ・コンポーネントなど）
- 同じ種類の既存の機能（「記事の一覧 API」なら、既存の一覧 API）
- テーブルを足すなら、スキーマ（`db/schema.rb`、`structure.sql`、migration、ORM のモデル定義など）

## 2. サブエージェントに読ませる

Agent ツール（subagent_type: Explore、model: sonnet）に、上の場所と下の観点を渡して読ませる。読むのは既存コードだけで、ファイルは編集させない。

| 観点 | 見ること |
|---|---|
| 名前空間・ディレクトリ | どの単位でディレクトリやモジュールを切っているか |
| ファイル名 | 単数・複数、接尾辞（`_service`、`.test.ts` など） |
| クラス・メソッド | 名前の付け方（動詞から始めるか、`call` 1つか）、1つのクラス・メソッドの大きさ |
| テーブル・カラム | テーブル名、中間テーブルの名前、外部キー・フラグ・日時のカラム名、インデックスの付け方 |
| テスト | 置き場所、ファイル名、ファクトリやフィクスチャの使い方 |

それぞれ、根拠にした既存のファイルを `path:line` で1つ以上添えさせる。流儀が場所によって割れているときは、新しいコード（最近のコミット）の方を採り、割れていることも書かせる。

## 3. メモにする

dev-flow.md があれば（`$(git rev-parse --git-dir)/dev-flow.md`）、「流儀のメモ」の節に書く。なければ結果として返す。

```markdown
## 流儀のメモ

- 名前空間: サービスは app/services/<ドメイン>/ に置く（app/services/articles/publish.rb:1）
- メソッド: サービスは公開メソッドを call 1つにする（app/services/articles/publish.rb:8）
- テスト: spec/services/<ドメイン>/ に同じ名前で置く（spec/services/articles/publish_spec.rb:1）
- 割れているところ: 日時のカラムは *_at と *_on が混在。新しいテーブルは *_at
```

メモは1項目1行にする。実装する人も、レビューする人も、これを読んで判断するため。

## 規律

- ファイルを編集しない。調べてメモにするまでがこの skill の仕事。
- 根拠のない項目は書かない。「一般的には〜」は流儀ではない。
