# /git-commit スキル

gitの差分や会話の文脈をもとに、[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) に従ったコミットメッセージを生成し、コミットを作成する

## 手順

### ステップ1: 現状把握

以下のコマンドを**並列**で実行:

- `git status`（`-uall` は使わない）
- `git diff --staged`
- `git diff`
- `git log --oneline -5`

直近のコミット履歴からメッセージの言語・スタイル・粒度を把握する

### ステップ2: ステージング判定

ステージ済みファイルがない場合:
- 会話の文脈・実装状況からステージすべきファイルを判断する

ステージ済みファイルがある場合はそのまま続行
複数の論理的変更が混在する場合は分割を提案する

### ステップ3: コードコメントの整理

コミット対象の差分で**追加・変更された行**のコメントを見直し、後述の「コードコメントの基準」に当たるものは簡略化するか削除する

- 対象は今回の差分に含まれるコメントだけ。既存のコメントには触れない
- 修正したファイルはステップ5で一緒にステージする
- 直した箇所はステップ5の確認で一覧にして見せる

### ステップ4: コミットメッセージ生成

変更理由が不明な場合はユーザーに質問する
後述の「コミットメッセージ規則」に従って生成し、日本語なら `humanizer-ja`、英語なら `humanizer:humanizer` スキルを読み込んでその基準で見直す

### ステップ5: ユーザー確認（1回のみ）

以下の内容をまとめて1回だけ確認する:

- **ステージ対象**: ステージするファイル一覧（既にステージ済みの場合はその旨）
- **コミットメッセージ**: 生成したメッセージ全文
- **整理したコメント**: ステップ3で簡略化・削除したコメント（ある場合のみ）

呼び出し元のスキル（`resolving-pr-reviews`）が確認をまとめて取る場合は、この確認を省いてそのままコミットする。その場合は上の3点を呼び出し元に渡し、呼び出し元の確認で見せてもらう

承認後、以下を順次実行:
1. ファイルのステージ（必要な場合）: `git add` で個別にステージ
2. コミット実行（HEREDOC形式）:

```bash
git commit -m "$(cat <<'EOF'
コミットメッセージ1行目

本文（必要な場合）
EOF
)"
```

### ステップ6: hook失敗時の対応

pre-commit hookが失敗した場合:

1. エラー内容を分析し、問題を修正する
2. 修正ファイルを再ステージ
3. **新規コミット**を作成する（hookの失敗時はコミットが未作成のため、`--amend` は前のコミットを書き換えてしまう）

## コードコメントの基準

コメントに残すのは、コードを読んでも分からないこと（なぜそうしたか、制約、外部仕様、ハマりどころ）だけにする

削るもの:

- コードをそのまま言い換えたもの（`# ユーザーを取得する` の下に `user = find_user`）
- 変更の経緯や作業メモ（`# 〜を修正`、`# 以前は〜だった`、`# 新しく追加`）。それはコミットメッセージに書く
- 関数名・引数名から明らかな内容を繰り返す docstring
- 区切りや飾りのためだけのコメント行
- 「重要:」「注意:」などのラベルだけで中身のない強調
- `humanizer-ja` の癖（大げさな言葉、念押し、翻訳調）を含むもの。残す場合も書き直す

短くするもの:

- 1行で言えることを複数行で書いている
- 同じ説明を複数箇所に書いている

## コミットメッセージ規則

### 言語

直近のコミット履歴と同じ言語で書く。履歴がない、または言語が混在している場合は英語にする

以下の記述ルールとテンプレートは日本語の場合のもの。英語の場合は「英語の場合」に従う

### 記述ルール

- 句点（。）は使わず、文の区切りでは改行する
- 本文は文字数で折り返さない　改行を入れるのは文や段落の区切りだけにする
- 本文は敬体で記述する
- **1行目**・**「なぜ必要なのか？」**・**「変更内容」**にはコード要素（クラス名・メソッド名・変数名）を含めず、コードを見たことがない人でも分かる文章で説明する
- **1行目**: 体言止め、50文字以内（最大72文字）　末尾に句読点・絵文字は付けない
- 技術用語は公式表記を使う（GitHub, RuboCop, TypeScript, Next.js, PostgreSQL, nginx 等）

### 変更理由（why）の記載

変更内容（what）は `git diff` で確認できるため、コミットメッセージには変更理由（why）を記載する
diffの情報より**会話の文脈**を優先し、以下を読み取る:

- 何が問題だったのか（背景・課題）
- このコミットでどう改善されるのか（効果・目的）

typo修正など自明な変更を除き、変更が必要だった理由を記載する

「不要」「不適切」「古い」などの主観的な判断を含む場合は、客観的な根拠（検索結果、意思決定の経緯、技術的事実、エラーの証拠、数値データ等）を添える

### テンプレート

本文が必要な場合:

```
型: 変更内容の要約（体言止め）

## 🎯 なぜ必要なのか？

[チケットの題名](チケットのURL) の対応です

~のためです（背景・課題の説明）
~のため、~します（課題と、それに対する対応方針の説明）

## 🔧 変更内容

### [絵文字] [見出し]

[詳細]

## 📎 参考

- [タイトル](URL)
```

- チケット（Notion・GitHub Issue）がある場合、「なぜ必要なのか？」の先頭に `[チケットの題名](チケットのURL) の対応です` の1行を置き、空行を挟んでから背景・課題の説明を続ける
  - チケットがない場合はこの行を省略する
  - この行は散文とは別の独立した要素として扱い、1行であっても後ろに空行を置く
- 「なぜ必要なのか？」「変更内容」は箇条書きにせず散文で記述し、話題が変わるところで段落を分ける
  - 段落の区切りに空行を入れるのは、段落が複数行にわたる場合のみとする
  - 1行で完結する記述が並ぶ場合は、空行を入れず改行のみで続ける
- 「なぜ必要なのか？」は背景・課題の説明だけで終わらせず、「~のため、~します」の形で対応方針を述べて締める
- 参考セクションは根拠リンクがある場合のみ追加する
- 見出しの後には必ず空行を入れる
- 見出しの絵文字は重複させない
  - 大見出し（`##`）は 🎯 / 🔧 / 📎 で固定する
  - 中見出し（`###`）には大見出しで使った絵文字（🎯・🔧・📎）を使わず、変更種別系の絵文字から選ぶ
  - 中見出しが複数ある場合も、それぞれ異なる絵文字を使う

### 図解

処理の流れ・状態遷移・構成の変化など、文章より図のほうが早く伝わる内容は、「変更内容」を ASCII アートの図で書く。図はコードブロックで囲む

全角文字は表示幅が半角2文字分になり、左右に並べると列がずれやすいので、変更前と変更後は上下に並べる

````
## 🔧 変更内容

### ♻️ 通知の送り先ごとに処理を分けました

```
変更前
  通知 ─► 送信処理 ─┬─ メールなら〜
                    ├─ Slack なら〜
                    └─ プッシュ通知なら〜

変更後
  通知 ─► 送り先の選択 ─┬─► メール送信
                        ├─► Slack 送信
                        └─► プッシュ通知送信
```
````

図だけで伝わるなら、図の説明を文章で繰り返さない。「なぜ必要なのか？」は図にせず散文で書く

本文を省略できるのは「なぜ」が自明な場合のみ（typo修正、lint修正等）
「不要コード削除」は省略不可

### 英語の場合

日本語の記述ルールのうち、次のものはそのまま適用する:

- 本文は文字数で折り返さない
- 1行目・「Why?」・「Changes」にはコード要素を含めない
- 変更理由（why）を書く、主観的な判断には根拠を添える
- 見出しの絵文字と空行の決まり、図解の書き方

次のものは英語の書き方に置き換える:

- **1行目**: `型: ` の後を大文字で始まる命令形にする（`feat: Add the review loop`）。末尾にピリオドは付けない
- 本文は文末にピリオドを付けた普通の文で書く。文と文の区切りで改行する
- 大見出しは `## 🎯 Why?` / `## 🔧 Changes` / `## 📎 References`
- チケットがある場合の1行目は `This addresses [チケットの題名](チケットのURL).`

```
feat: Add the review loop

## 🎯 Why?

Each round of review fixes had to be started by hand, and Copilot often leaves new comments around the lines that were just fixed.
The skill now repeats the round until no new comments arrive, stopping only before a push.

## 🔧 Changes

### ✨ Request a re-review and wait for it

After each push, Copilot is asked for another review and the skill waits for it in the background.
```

### Conventional Commits prefix

参考: [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) / [Angular Commit Message Guidelines](https://github.com/angular/angular/blob/22b96b9/CONTRIBUTING.md#-commit-message-guidelines)

prefixは原則必須:

| prefix | 用途 |
|--------|------|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `chore` | リリースノートに書く必要のない作業 |
| `refactor` | バグ修正でも新機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `style` | コードの意味に影響しない変更 |
| `test` | テストの追加・修正 |
| `docs` | ドキュメントのみの変更 |
| `ci` | CI設定の変更 |
| `build` | ビルドシステムや外部依存関係の変更 |
| `remove` | コードやファイルの削除 |

破壊的変更がある場合は型の後に `!` を付ける（例: `feat!: APIレスポンスの形式を変更`）

### 絵文字

詳細は [gitmoji.dev](https://gitmoji.dev) 参照

見出し系（大見出し `##` 用）: 🎯 目的・背景 / 🤔 課題・問題 / 🔧 変更内容 / 📎 参考

変更種別系: ✨ 新機能 / 🐛 バグ修正 / 🚑️ 緊急修正 / ♻️ リファクタ / 🔥 削除 / ⚡️ パフォーマンス / 🔒️ セキュリティ / 💄 UI/UX / ✅ テスト / 📝 ドキュメント / 🌐 国際化 / ⬆️ 依存関係更新 / 👷 CI/CD / 💥 破壊的変更

## 禁止事項

- `git push` はユーザーが明示的に依頼した場合のみ実行する
  - リモートへの反映は取り消しが難しく、レビュー前の変更が共有ブランチに乗ってしまうため
- `--no-verify` は使わない
  - lintやシークレット検査などのpre-commit hookを素通りさせ、問題のあるコードがそのまま履歴に残るため
