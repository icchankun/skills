# writing-slack-messages

Slack に貼る文章を作る。投稿はしない。貼って送るのはユーザー。

## 1. 何を書くか確かめる

次の3つを会話から拾う。足りないものだけ聞く。

- 宛先: チャンネルか DM か、スレッドへの返信か。誰が読むか
- 目的: 共有・相談・依頼・返信のどれか。読んだ人に何をしてほしいか
- 中身: 伝える事実、決まったこと、期限（あれば）

返信なら、返す元の発言を貼ってもらう。

## 2. 下書きを書く

最初から Slack の書式（mrkdwn）で書く。Markdown で書いて後から変えると、変換の漏れが出るため。

| 書きたいもの | Slack の書式 |
|---|---|
| 太字 | `*太字*` |
| 斜体 | `_斜体_` |
| 取り消し線 | `~取り消し~` |
| コード | `` `code` ``、複数行は ```` ``` ```` で囲む |
| 引用 | 行頭に `>` |
| 箇条書き | 行頭に `• ` |
| メンション | `@名前`（ユーザーが貼ったあとに Slack の候補から選び直す） |

- リンクは URL をそのまま書く。`<URL|文字>` は API で投稿するときの書き方で、入力欄に貼ってもリンクにならない。
- 見出し（`#`）と表は Slack にないので使わない。見出しが要るなら `*太字*` の1行にする。
### 文体

- です・ます調で書く
- 句点（。）は付けず、文の区切りで改行する

### 1行目

1行目は `【種類】用件` にする。通知には冒頭の20〜30字しか出ず、読む人はそこで開くかを決めるため。

- 【至急】: 障害、セキュリティの検知など。すぐ見て判断してほしい
- 【依頼】: レビュー、作業、承認など。それをしてほしい
- 【相談】: 設計や方針の判断。方向を決めてほしい
- 【確認】: 仕様や設定値が合っているか。合否を返してほしい
- 【報告】: 終わった作業、進み具合。リアクションで足りる
- 【共有】: 参考の情報。返事は要らない

### 長さ

- 理由や詳細もスレッドに分けず、1つのメッセージに書く。結論と依頼を先に置けば、長くても読む人は要るところで止められる
- 前に同じ説明をしていれば、繰り返さずにそのリンクを貼る
- 削るもの
  - 余計な修飾語（「革新的な」）と、余計な敬語（「〜させていただきます」は「〜します」）
  - メンションの後の「さん」
  - 挨拶。ただし、その日はじめて送る相手には付ける

### 曖昧にしない

- いつ頃かと数は書く。「後で連絡します」「少し足りないです」とは書かない
- 作業の状態をはっきり書く。「できると思います」ではなく「12/3 に直しも込みで終わります」
- 「よろしくお願いします」で済ませず、相手にしてほしいことを書く
- 意見はぼかさない。「自分はこう思いますが……」で止めず、どうしたいかまで書く
- 読む人で意味が割れる言葉は、具体的な言葉にする（「コピー」なら「キャッチコピー」か「本文」か）

### 読みやすさ

- 並べるものは `• ラベル: 値` の箇条書きにする。段落にまとめると読むのに手間がかかり、後回しにされる
- 主語と述語を離さない
- 漢字は開けるものは開く（「下さい」は「ください」、「事」は「こと」、「及び」は「および」）

### 気持ちを添える

文字だけだと、思っているより冷たく伝わる。

- お礼やねぎらいは多めに書く（「ありがとうございます、助かります」）
- 頼むときは「〜いただけると助かります」「〜お願いできますか」とやわらかく書く。「〜してください」「返してもらえますか」は指示に聞こえる
- 責める言い方はしない（「前にも説明したはずですが」「言っている意味がわからないです」）
- 直してほしいことを伝えるときは、よかったことと、この先への期待で挟む

### メンション

- `@channel` と `@here` は、障害や全員に関わる急ぎの知らせのときだけ使う。ふだんから使うと、大事な知らせも読まれなくなる
- 何人かに送るときは、動いてほしい人と、知っておいてほしいだけの人を分けて書く（`@名前（レビューをお願いします）`、`cc: @名前`）
- 業務時間の外に送るときは、送信の予約を勧める。すぐ送るなら冒頭に「返事は明日で大丈夫です」と添える

### ログとコード

- 1〜2行のコマンドや名前は `` `code` ``、3〜10行の抜粋は ```` ``` ```` で囲む
- それより長いログは本文に貼らず、要のところ（3〜5行）だけを本文に残し、全体はファイルで付ける
- ログには、打ったコマンドと時刻、見てほしい箇所、期待した結果と今の見立てを添える。ログだけを貼らない

### 質問・確認・依頼・相談の型

1行目のあとに、次の順で書く。

1. 事実: 何が起きているか。数や場所など、確かめたことだけを書く
2. 自分の理解・判断: 自分はどう考えているか。根拠があれば添える
3. 聞きたいこと: 相手に何を求めているか

依頼と相談は、最後に次のことを書いて締める。誰がと何をするが欠けると、誰も動かない。

- 誰が: `@名前` で名指しする。決まっていなければ「誰か拾えますか？」と書く
- いつまでに: リリースの日など、決まった期限があるときだけ書く
- 何をする: 返事をする、レビューする、決めるなど、してほしいことを書く

相談は、会議で話さなくても文だけで決められるように、2. を次の形にする。案を並べずに「どうしましょう？」と聞くと、相手が案から考えることになる。

- 目的: 何のために決めたいか、決めると何がよくなるか
- 案: 選べる案を2〜3個、それぞれ1行で
- 評価の軸: 何で比べたか（手間、速さ、影響の範囲など）
- 自分の案: 軸に照らしてどれがよいか、その理由

```
【相談】公開日時前の記事の詳細ページをどう扱うか

記事の公開日時を未来にすると、一覧には出ませんが、詳細ページは URL を直接開くと見えてしまいます
公開前の記事が外から読まれないようにしたいです

案は2つあります
• A: 公開日時までは 404 にする
• B: 詳細は見せたまま、検索エンジンにだけ載せないようにする

公開前に読まれないか、直す手間で比べると、A がよいと考えています
B では URL を知っている人に読まれてしまい、A も商品の販売開始前のページと同じ作りで済むためです

@名前 A で進めてよいか、ご確認いただけると助かります
```

## 3. 見直す

`reviewing-writing` で見直す。Slack の書式の記号は崩さない。

## 4. 見せて確認する

下書きをコードブロックに入れて見せる。コードブロックの中は、そのままクリップボードに入る文字そのものにする。

直すよう言われたら、直したものをもう一度見せて確認する。OK が出るまでコピーしない。

## 5. クリップボードにコピーする

OK が出た文を一時ファイルに書き、`pbcopy` でコピーする。シェルの引数に直接渡すと、記号や改行が崩れるため。

```bash
cat > <scratchpad>/slack.txt <<'EOF'
<OK が出た文>
EOF
pbcopy < <scratchpad>/slack.txt
```

コピーしたら、その旨と、メンションがあれば Slack で選び直すことを伝えて終える。
