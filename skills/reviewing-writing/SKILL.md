# reviewing-writing

人が読む、会話の外に残る文章を、出す前に見直す。言っている内容は変えない。事実・数値・固有名詞・リンク・コードは足しも削りもしない。

呼び出し元が決めている書式（committing-git-changes の句点なし・敬体、見出しの形、writing-slack-messages の1行目の【種類】・`• ラベル: 値` の箇条書き・お礼など）はそのまま守る。humanizer-ja の癖に当たっても直さない。

## 1. textlint で表記を確かめる

日本語の文章のときだけ行う。下書きを一時ファイルに書き、同梱の設定で textlint を通す。

```bash
npx -y -p textlint@14 -p textlint-rule-preset-ja-technical-writing@12 \
  textlint --config <skill のディレクトリ>/textlintrc.json <一時ファイル>
```

- 設定は ja-technical-writing のうち、文末の句点を求めるルールと `？` を禁じるルールだけを切っている。コミットメッセージの書式とぶつかるため。
- 出た指摘は直す。ただしコード・コマンド・固有名詞の中で出たものは直さない。
- npx が使えない、ネットワークがないなどで動かないときは飛ばし、結果の先頭にその旨を書く。

## 2. 観点ごとに見直す

次の3つを、それぞれ別のサブエージェントに並列で頼む。下書きと文章の種類、呼び出し元が決めている書式を渡し、「直す箇所と直した文」を返してもらう。直す箇所がなければ「なし」と返してもらう。観点が決まっていて、1つずつ当てるだけなので、標準のモデルでよい。サブエージェントを使えないときは、3つの観点を順に自分で当てる。

書いた本人が見直すと、自分の言い回しを正しいと思い込みやすい。観点ごとに別の目で見るのはそのため。

下書きが20行未満（レビューへの返信、動作確認の項目、短いコミットメッセージなど）なら、3つの観点をまとめて1つのサブエージェントに頼む。短い文では観点ごとに分けても見つかるものが変わらず、起動の数だけトークンが増えるため。

### 削る・つなげる

```text
1. この文は要るか？      → 要らなければ削る
2. 他の箇所で言っていないか？ → 重複なら削る
3. つなげた方が分かるか？  → 主語が同じ短い文が続く、理由と結論が別の文に分かれている、などは1文にする
```

要らない文は、読み手がこの文章で判断や作業をするのに使わない文。次のものは、読み手の判断に関わると言えない限り削る。

- 作業の経緯や試した過程（「最初は〜を試しました」「〜で詰まりました」）
- 調べていないこと・確かめていないことの断り書き（「原因は調べていません」）
- 読み手が何もしなくてよい後始末や予定（「マージ後に close します」）
- 背景の説明に入れた細かい数値（件数・秒数・割合）

1文の中の冗長な言い回し（「〜することができる」「〜を行う」など）は、次の AI っぽさの観点で humanizer-ja が直すので、ここでは見ない。同じ直しが2回出ないようにするため。

### AI っぽさ

`humanizer-ja` の観点で見る。英語の文章の扱いも humanizer-ja に従う。

### 図にするか

分岐・状態の移り変わり・構成・変更前と変更後など、図で表せる箇所を探し、ASCII アートの図にした案を返す。一列に進むだけの手順は図にせず、番号付きの箇条書きにする。迷ったら図にする。すでにある図も、決まりに沿っていなければ直した案を返す。

- 図の決まりと型は `<skill のディレクトリ>/references/diagrams.md` に従う。
- 図はコードブロックで囲む。
- 図で伝わるなら、図の説明を文章で繰り返さない。
- 図で表せる箇所がないときだけ「なし」と返す。

## 3. まとめて直す

3つの結果を下書きに反映する。同じ箇所に別々の直し方が出たら、短い方を採る。

直した文を読み返し、内容が欠けていないか、足していないかを確かめてから返す。

## 返すもの

- 呼び出し元のスキルから使うときは、仕上がった文だけを返す。
- ユーザーに頼まれたときは、仕上がった文と、直した箇所の短い一覧を返す。
