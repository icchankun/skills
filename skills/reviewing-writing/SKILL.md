# reviewing-writing

会話の外に残る文章を、出す前に見直す。言っている内容は変えない。事実・数値・固有名詞・リンク・コードは足しも削りもしない。

呼び出し元が決めている書式（committing-git-changes の句点なし・敬体、見出しの形など）はそのまま守る。

## 1. textlint で表記を確かめる

日本語の文章のときだけ行う。下書きを一時ファイルに書き、同梱の設定で textlint を通す。

```bash
npx -y -p textlint@14 -p textlint-rule-preset-ja-technical-writing@12 \
  textlint --config ~/.claude/skills/reviewing-writing/textlintrc.json <一時ファイル>
```

- 設定は ja-technical-writing のうち、文末の句点を求めるルールと `？` を禁じるルールだけを切っている。コミットメッセージの書式とぶつかるため。
- 出た指摘は直す。ただしコード・コマンド・固有名詞の中で出たものは直さない。
- npx が使えない、ネットワークがないなどで動かないときは飛ばし、結果の先頭にその旨を書く。

## 2. 観点ごとに見直す

次の3つを、それぞれ別のサブエージェント（Agent ツール、`model: sonnet`）に並列で頼む。下書きと文章の種類を渡し、「直す箇所と直した文」を返してもらう。直す箇所がなければ「なし」と返してもらう。

書いた本人が見直すと、自分の言い回しを正しいと思い込みやすい。観点ごとに別の目で見るのはそのため。

### 削る・つなげる

```
1. この文は要るか？      → 要らなければ削る
2. 他の箇所で言っていないか？ → 重複なら削る
3. もっと短くできないか？  → 1文に縮める
4. つなげた方が分かるか？  → 主語が同じ短い文が続く、理由と結論が別の文に分かれている、などは1文にする
```

冗長な言い回しは短くする（「〜することができる」→「〜できる」、「〜という形になります」→「〜になります」、「〜を行う」→「〜する」）。

### AI っぽさ

`humanizer-ja` の観点で見る。英語の文章なら `humanizer:humanizer`。

### 図にするか

処理の流れ・状態の移り変わり・構成の変化・変更前と変更後など、文章より図の方が早く伝わる箇所を探し、ASCII アートの図にした案を返す。

- 図はコードブロックで囲む。
- 全角文字は幅が半角2文字分になり列がずれやすいので、変更前と変更後は左右ではなく上下に並べる。
- 図で伝わるなら、図の説明を文章で繰り返さない。
- 図にするほどでないなら「なし」と返す。無理に図にしない。

## 3. まとめて直す

3つの結果を下書きに反映する。同じ箇所に別々の直し方が出たら、短い方を採る。

直した文を読み返し、内容が欠けていないか、足していないかを確かめてから返す。

## 返すもの

- 呼び出し元のスキルから使うときは、仕上がった文だけを返す。
- ユーザーに頼まれたときは、仕上がった文と、直した箇所の短い一覧を返す。
