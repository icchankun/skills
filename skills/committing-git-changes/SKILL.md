# committing-git-changes

gitの差分や会話の文脈をもとに、[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) に従ったコミットメッセージを生成し、コミットを作成する

## 手順

### ステップ1: 現状把握

以下のコマンドを**並列**で実行:

- `git status`（`-uall` は使わない）
- `git diff --staged`
- `git diff`
- `git log --oneline -5`

直近のコミット履歴からメッセージの言語・スタイル・粒度を把握する

### ステップ2: ステージング判定

ステージ済みファイルがない場合:
- 会話の文脈・実装状況からステージすべきファイルを判断する

ステージ済みファイルがある場合はそのまま続行
複数の論理的変更が混在する場合は分割を提案する

### ステップ3: コードコメントの整理

コミット対象の差分で**追加・変更された行**のコメントを見直し、`<skill のディレクトリ>/references/comments.md` の基準に当たるものは簡略化するか削除する

- 対象は今回の差分に含まれるコメントだけ。既存のコメントには触れない
- 残したコメントのうち、今回足したか書き換えたものは `reviewing-writing` で見直し、返ってきた文に差し替える。ステップ4のメッセージの見直しと同時に頼んでよい
- 修正したファイルはステップ5で一緒にステージする
- 直した箇所はステップ5の確認で一覧にして見せる

### ステップ4: コミットメッセージ生成

「なぜ必要なのか？」はエージェントが考えるものではなく、作業の前に人間が決めたものを書く
dev-flow.md（`$(git rev-parse --absolute-git-dir)/dev-flow.md`）に「なぜ」があれば、それを元に書き、推測で足さない
なければ書く前にユーザーに質問する　typo修正など、なぜが自明な場合は聞かない
`<skill のディレクトリ>/references/message.md` の規則（言語・記述ルール・テンプレート・図解・prefix・絵文字）に従って生成する
テーブルやカラムの変更・API の追加など、型が決まっている種類の変更は、あわせて `<skill のディレクトリ>/references/templates.md` の型に沿って書く

生成したら、中見出しの絵文字が gitmoji の公式一覧にあるかをスクリプトで確かめる:

```bash
python3 <skill のディレクトリ>/scripts/check_gitmoji.py < <メッセージのファイル>
```

- 終了コード 1 は一覧にない絵文字がある。出力された見出しの絵文字を、一覧から選び直す
- 終了コード 2 は一覧を取れなかった。飛ばして続ける

そのあと次の2つを並列で行い、両方の結果を反映する:

- `reviewing-writing` スキルで文章を見直す
- サブエージェントに、差分とメッセージを渡し、中見出しの絵文字が変更の種類に合っているかを確かめさせる。一覧にある絵文字でも、新機能に 🐛 を付けるような取り違えはスクリプトでは見つからないため　見比べるだけの軽い作業なので、いちばん軽いモデル（Claude Code は `haiku`、Codex は `gpt-6-luna`）でよい　サブエージェントを使えないときは自分で確かめる

### ステップ5: ユーザー確認

以下の内容をまとめて確認する:

- **ステージ対象**: ステージするファイル一覧（既にステージ済みの場合はその旨）
- **コミットメッセージ**: 生成したメッセージ全文
- **整理したコメント**: ステップ3で簡略化・削除したコメント（ある場合のみ）

メッセージを直すよう言われたら、直したものを見せてもう一度確認する　承認されるまでコミットしない
dev-flow.md があれば、確認を出す前に状態を `ユーザー待ち` にする　ユーザーが返事をすると hook が `作業中` に戻す

呼び出し元のスキル（`resolving-pr-reviews`）が確認をまとめて取る場合は、この確認を省いてそのままコミットする。その場合は上の3点を呼び出し元に渡し、呼び出し元の確認で見せてもらう

承認後、以下を順次実行:
1. ファイルのステージ（必要な場合）: `git add` で個別にステージ
2. コミット実行（HEREDOC形式）:

```bash
git commit -m "$(cat <<'EOF'
コミットメッセージ1行目

本文（必要な場合）
EOF
)"
```

### ステップ6: hook失敗時の対応

pre-commit hookが失敗した場合:

1. エラー内容を分析し、問題を修正する
2. 修正ファイルを再ステージ
3. **新規コミット**を作成する（hookの失敗時はコミットが未作成のため、`--amend` は前のコミットを書き換えてしまう）

## 禁止事項

- `git push` はユーザーが明示的に依頼した場合のみ実行する
  - リモートへの反映は取り消しが難しく、レビュー前の変更が共有ブランチに乗ってしまうため
- `--no-verify` は使わない
  - lintやシークレット検査などのpre-commit hookを素通りさせ、問題のあるコードがそのまま履歴に残るため
