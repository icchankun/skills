# コミットメッセージ規則

ステップ4でメッセージを書くときに従う。

## 言語

直近のコミット履歴と同じ言語で書く。履歴がない、または言語が混在している場合は英語にする

以下の記述ルールとテンプレートは日本語の場合のもの。英語の場合は「英語の場合」に従う

## 記述ルール

- 句点（。）は使わず、文の区切りでは改行する
- 1文の読点は3つまでにし、それを超えるなら分ける
- 本文は文字数で折り返さない　改行を入れるのは文や段落の区切りだけにする
- 本文は敬体で記述する
- **1行目**・**「なぜ必要なのか？」**・**「変更内容」**にはコード要素（クラス名・メソッド名・変数名）を含めず、コードを見たことがない人でも分かる文章で説明する
- **1行目**: 体言止め、50文字以内（最大72文字）　末尾に句読点・絵文字は付けない
- 技術用語は公式表記を使う（GitHub, RuboCop, TypeScript, Next.js, PostgreSQL, nginx 等）

## 変更理由（why）の記載

変更内容（what）は `git diff` で確認できるため、コミットメッセージには変更理由（why）を記載する
diffの情報より**会話の文脈**を優先し、以下を読み取る:

- 何が問題だったのか（背景・課題）
- このコミットでどう改善されるのか（効果・目的）

typo修正など自明な変更を除き、変更が必要だった理由を記載する

「不要」「不適切」「古い」などの主観的な判断を含む場合は、客観的な根拠（検索結果、意思決定の経緯、技術的事実、エラーの証拠、数値データ等）を添える

## テンプレート

本文が必要な場合:

```
型: 変更内容の要約（体言止め）

## 🎯 なぜ必要なのか？

[チケットの題名](チケットのURL) の対応です

~のためです（背景・課題の説明）
~のため、~します（課題と、それに対する対応方針の説明）

## 🔧 変更内容

### [絵文字] [見出し]

[補足の文]

[図]

## 📎 参考

- [タイトル](URL)
```

- チケット（Notion・GitHub Issue）がある場合、「なぜ必要なのか？」の先頭に `[チケットの題名](チケットのURL) の対応です` の1行を置き、空行を挟んでから背景・課題の説明を続ける
  - チケットがない場合はこの行を省略する
  - レビューコメントへの対応のコミットでは、チケットの代わりに `[レビューコメント](レビューコメントのURL) の対応です` を置く。1つのコミットで複数のコメントに対応したときは、次のように URL を箇条書きで並べる

    ```
    以下のレビューコメントの対応です
    - レビューコメントのURL
    - レビューコメントのURL
    ```

  - この行は散文とは別の独立した要素として扱い、1行であっても後ろに空行を置く
- 「なぜ必要なのか？」と、「変更内容」の補足の文は箇条書きにせず散文で記述し、話題が変わるところで段落を分ける
  - 段落の区切りに空行を入れるのは、段落が複数行にわたる場合のみとする
  - 1行で完結する記述が並ぶ場合は、空行を入れず改行のみで続ける
- 「なぜ必要なのか？」は背景・課題の説明だけで終わらせず、「~のため、~します」の形で対応方針を述べて締める
- 参考セクションは根拠リンクがある場合のみ追加する
- 見出しの後には必ず空行を入れる
- 中見出し（`###`）の下には必ず本文を1文以上書く。本文にするほどの内容がない変更は、中見出しを立てずに近い中見出しの本文に含める
- 見出しの絵文字は重複させない
  - 大見出し（`##`）は 🎯 / 🔧 / 📎 で固定する
  - 中見出し（`###`）には大見出しで使った絵文字（🎯・🔧・📎）を使わず、変更種別系の絵文字から選ぶ
  - 中見出しが複数ある場合も、それぞれ異なる絵文字を使う

## 図解

「変更内容」は図を主にして書く。中見出しごとに、分岐・状態の移り変わり・構成・変更前と変更後・テーブルの関係のどれかで表せるなら ASCII アートの図にし、補足を図の上に1〜2文で書く

図を描く前に `<skill のディレクトリ>/../reviewing-writing/references/diagrams.md` を読み、その決まりと型に沿って描く。図はコードブロックで囲む

````
## 🔧 変更内容

### ♻️ 通知の送り先ごとに処理を分けました

送り先を足すときは、送り先の選択に1つ足すだけで済みます

```
変更前
  通知
  `-> 送信処理
      |-> メールなら〜
      |-> Slack なら〜
      `-> プッシュ通知なら〜

変更後
  通知
  `-> 送り先の選択（追加）
      |-> メール送信
      |-> Slack 送信
      `-> プッシュ通知送信
```
````

補足には、図に書けないこと（なぜその形にしたか、制約、何に倣ったか）を書き、図で分かることを文で繰り返さない
「なぜ必要なのか？」は図にせず散文で書く

## 種類ごとの型

テーブルやカラムの変更、API の追加のように、書くことが決まっている変更は `<skill のディレクトリ>/references/templates.md` の型に沿って書く。テーブルやカラムの変更では、テーブル同士の関係とカラムを ASCII アートの図にする。PR では creating-pull-requests がこの図を mermaid の ER 図に置き換える

本文を省略できるのは「なぜ」が自明な場合のみ（typo修正、lint修正等）
「不要コード削除」は省略不可

## 英語の場合

日本語の記述ルールのうち、次のものはそのまま適用する:

- 本文は文字数で折り返さない
- 1行目・「Why?」・「Changes」にはコード要素を含めない
- 変更理由（why）を書く、主観的な判断には根拠を添える
- 「Why?」は背景・課題の説明だけで終わらせず、対応方針を述べて締める。英語では課題の文に `, so …` でつなぐか、最後の文を `… so …` の形にする
- 見出しの絵文字と空行の決まり、中見出しの下に本文を書くこと、図解の書き方

次のものは英語の書き方に置き換える:

- **1行目**: `型: ` の後を大文字で始まる命令形にする（`feat: Add the review loop`）。末尾にピリオドは付けない
- 本文は文末にピリオドを付けた普通の文で書く。文と文の区切りで改行する
- 大見出しは `## 🎯 Why?` / `## 🔧 Changes` / `## 📎 References`
- チケットがある場合の1行目は `This addresses [チケットの題名](チケットのURL).`
- レビューコメントへの対応なら `This addresses [the review comment](レビューコメントのURL).`、複数なら `This addresses the following review comments:` の下に URL を箇条書きで並べる

```
feat: Add the review loop

## 🎯 Why?

Each round of review fixes had to be started by hand, and Copilot often leaves new comments around the lines that were just fixed.
Waiting for those comments by hand made every fix take several turns, so the skill now repeats the round until no new comments arrive, stopping only before a push.

## 🔧 Changes

### ✨ Request a re-review and wait for it

After each push, Copilot is asked for another review and the skill waits for it in the background.
```

## Conventional Commits prefix

参考: [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) / [Angular Commit Message Guidelines](https://github.com/angular/angular/blob/22b96b9/CONTRIBUTING.md#-commit-message-guidelines)

prefixは原則必須:

| prefix | 用途 |
|--------|------|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `chore` | リリースノートに書く必要のない作業 |
| `refactor` | バグ修正でも新機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `style` | コードの意味に影響しない変更 |
| `test` | テストの追加・修正 |
| `docs` | ドキュメントのみの変更 |
| `ci` | CI設定の変更 |
| `build` | ビルドシステムや外部依存関係の変更 |
| `remove` | コードやファイルの削除 |

破壊的変更がある場合は型の後に `!` を付ける（例: `feat!: APIレスポンスの形式を変更`）

詳細は [gitmoji.dev](https://gitmoji.dev) 参照

変更種別系: ✨ 新機能 / 🐛 バグ修正 / 🚑️ 緊急修正 / ♻️ リファクタ / 🔥 削除 / ⚡️ パフォーマンス / 🔒️ セキュリティ / 💄 UI/UX / ✅ テスト / 📝 ドキュメント / 🌐 国際化 / ⬆️ 依存関係更新 / 👷 CI/CD / 💥 破壊的変更
