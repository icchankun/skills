# 種類ごとの型

型に当てはまる変更のときだけ使う。当てはまらない部分は無理に埋めず、見出しごと書かない。

## テーブルとカラムの変更

テーブルやカラムを足す・変える・消すときは、テーブル同士の関係とカラムを ASCII アートの図にする。図の決まりは `diagrams.md` に従う。

- テーブルは `名前 意味（印）` と書く。印は `（新規）` `（既存）`
- カラムは2つ字下げして `名前: 意味（印）` と書く。印は `（追加）` `（変更: 何をどう変えたか）` `（削除）`
- 書くカラムは、足した・変えた・消したものと、関係に使う外部キーだけにする。ほかは `...` で略す
- 型や制約は、判断が入ったものだけ意味の後ろに付ける（`、一意` `、必須`）
- 関係が一列なら `| 1 : *` と `v` で縦につなぎ、2つ以上の先へ分かれるなら `|->` `` `-> `` で分けて多重度を行の最後に書く
- 補足は図の上に書く。似た既存のテーブルに倣ったなら何に倣ったか（「商品と同じく」）、用意した操作（追加・削除・入れ替えなど）、既にある行の値をどうしたか（初期値・埋め直し）を書く

テーブルを足すとき:

````
### 🗃️ 記事とタグを紐づけるテーブルを追加

商品と同じく、記事ごとにタグを付けるテーブルと、おすすめに出すかのフラグを足し、タグの追加・削除・入れ替えの操作も商品と同じものを用意しました
既にある記事のフラグは、おすすめに出さない値で埋めています

```
posts 記事（既存）
  featured: おすすめに出すか（追加）
  |
  | 1 : *
  v
post_taggings 記事とタグの紐づけ（新規）
  post_id: 記事
  tag_id: タグ
  |
  | * : 1
  v
tags タグ（既存）
```
````

1つのテーブルから2つ以上の先へつながるとき:

```
users ユーザー（既存）
  |-> posts 記事（既存）  1 : *
  `-> notifications 通知（新規）  1 : *
        user_id: ユーザー
        read_at: 読んだ日時
```

カラムだけを変えるとき:

````
### 🗃️ ユーザーに最後に通知した日時を持たせる

通知を送りすぎないように最後に送った日時を残し、表示名は空のまま登録できないようにしました
既にある空の表示名は、メールアドレスの @ より前で埋めています

```
users ユーザー（既存）
  ...
  notified_at: 最後に通知した日時（追加）
  nickname: 表示名（変更: 必須に）
  legacy_code: 旧システムの番号（削除）
```
````

## API の追加

エンドポイントごとに、メソッドとパスを書き、レスポンスの形を json5 で書く。各フィールドの意味は行末のコメントに書く。

````
## 🔧 変更内容

下書き・非公開・公開日時の前の記事は返しません
商品の販売終了と同じく、公開期間が終わった記事も返しません

### ✨ 追加する API

`GET /api/posts`

```json5
{
  posts: [ /* 詳細と同じ形の記事 */ ], // 公開日時の新しい順。同じなら後に登録したものが先
}
```

`GET /api/posts/:slug`

```json5
{
  slug: "...",                // 記事の URL 用の識別子
  title: "...",               // 記事の題名
  published_at: "...",        // 公開日時
  cover_image: {              // 表紙の画像
    url: "...",               // 画像の URL
    width: 1200,              // 幅（px）
    height: 630,              // 高さ（px）
  },
}
```

画像を入れ子にしているのは、サムネイルなど別の大きさを足すときに同じ形で並べられるようにするためです
一覧はページを分けずに全件を返します
フィーチャーフラグが無効な場合は一覧も詳細も 404、公開中でない記事の詳細も 404 を返します
````

- 何を返さないか（絞り込みの条件）を先に書く
- 並び順は配列のフィールドのコメントに書く
- 形を決めた理由（入れ子にした理由など）と、ページ分け・エラー時の返し方を最後に書く
