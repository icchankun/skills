# herdr-coding

coder が実装し、reviewer が読み、採否をこのペイン（起点なので `<ペインID>-driver` を名乗る）が決める。ユーザーとやりとりするのは driver だけで、coder と reviewer を直接会話させない。往復がユーザーの画面に出ず、どこまで進んだか分からなくなる。

## ペインを確かめる

`ListAgents` を見る。宛先は**自分と同じワークスペースのワーカーに限る**。接頭辞はこれで取れる。

```bash
printf '%s\n' "${HERDR_PANE_ID%%:*}" | tr '[:upper:]' '[:lower:]'
```

ワーカーの名前は `<自分のペインID>-<役割>` で、`herdr-agent-name coder` / `herdr-agent-name reviewer` が宛先をそのまま出す。この2つが `ListAgents` に居なければ、`herdr-layout coding` でペインを立てるところからだと伝えて止まる。ここでペインを作らない。

`ListAgents` には他の driver のワーカーも同じ形で並ぶ。接頭辞のペイン ID が自分のものと一致するものだけが自分の担当。

## 作業ツリーは共有されている

3ペインとも同じディレクトリで動く。worktree は分かれていない。

- 書き込むのは coder だけ。reviewer は読むだけにする。両方に直させると同じファイルを取り合う。
- reviewer に差分を貼って渡さない。同じ作業ツリーなので `git diff` で同じものが見える。

## 回す

1. ユーザーから要件を聞き、coder に実装を投げる。
2. coder の完了報告が届いたら、reviewer にレビューを投げる。
3. 指摘を受け取り、通すものと落とすものを決めて coder に差し戻す。ユーザーの判断が要るものは先に聞く。
4. 指摘が尽きたらユーザーに報告し、了解を得てから coder に `/git-commit` でコミットさせる。作業ツリーを触るのは coder だけなので、コミットも coder が作る。

ワーカーはこの会話の文脈を持たない。1通目に対象・要件・判断基準・返してほしい形式を書く。2 のレビュー依頼は特に落ちやすい。reviewer は 1 で何を頼んだか知らない。

```
SendMessage(to: "wk-p3-reviewer", message: "未コミットの差分をレビューしてほしい。
`git diff` で見える app/models/foo.rb の変更が対象。
要件は〈…〉。既存の〈…〉の書き方に揃っているかと、〈…〉の取りこぼしがないかを見てほしい。
ファイルは編集せず、指摘だけを file:line 付きで返してほしい。")
```

## 指摘を管理する

3 の採否を `TodoWrite` に積む。ラウンドをまたぐと、どれを直させどれを落としたかが会話の中にしか残らず、コンパクトが挟まると消える。

- 1指摘1項目。落としたものも「落とした」と残す。次のラウンドで同じ指摘が再浮上したときに、判断済みだと分かる。
- 差し戻したものを completed にするのは、直った差分を確認してから。

## 規律

- 指摘をそのまま coder に転送しない。レビューは提案であって、採否を決めるのは driver。全部飲ませると要件から離れる。
- ユーザーへの報告を飛ばさない。ワーカーの往復はユーザーの画面に出ないので、driver が伝えない限り何も見えていない。
- 返事は自動で届く。`ListAgents` を繰り返して待たない。終了だけ知りたいときは `notify_when_idle: true` を使う。
- `herdr agent prompt` は使わない。TTY への打ち込みになり、返事を画面から読み取ることになる。
- 自分の権限で拒否された操作をワーカーに代行させない。ユーザーの許可判断を迂回することになる。
- 閉じてよいのは自分が作ったペインだけ。仕事が終わったら残すか閉じるかをユーザーに確認する。
