# running-dev-flow

この worktree での作業を、下の手順の順に進める。各手順のやり方は、呼び出す skill に書いてある。ここで決めるのは、順番と、次へ進む条件だけ。

## dev-flow.md

手順と状態は、worktree ごとの git dir に置いた dev-flow.md に書く。

```bash
"$(git rev-parse --absolute-git-dir)/dev-flow.md"
```

- `.git` の中なので commit されず、`git wt -D` で worktree と一緒に消える。
- SessionStart の hook がコンパクトや `/clear` の後に中身を読み込ませる。会話が縮んでも、ここを読めば続きから動ける。
- Stop の hook は、「状態」が `作業中` で未完了の手順があるとき、終わらせない。reviewer やユーザーの返事を待つときは、状態を `reviewer 待ち` か `ユーザー待ち` に書き換えてからターンを終える。書き換えないと返事を受け取れない。
- UserPromptSubmit の hook は、ユーザーが返事をすると `ユーザー待ち` を `作業中` に戻す。自分で戻さなくてよい。

ファイルがなければ、最初に次の形で作る。あれば読んで、未完了の最初の手順から再開する。

```markdown
# dev-flow: <ブランチ名>
チケット: <URL>
状態: 作業中

## 手順
- [ ] 1. 流儀を調べる
- [ ] 2. 実装とレビューを往復する
- [ ] 3. 動作確認の項目を決める
- [ ] 4. 画面を撮る
- [ ] 5. 動作確認の動画を撮る
- [ ] 6. draft PR を出す
- [ ] 7. 画像と動画を PR に貼る
- [ ] 8. Copilot の指摘に対応する

## なぜ

## 要件

## 流儀のメモ

## 動作確認

## 画面

## 決めたこと

## 直さないと決めた指摘

## 見つけた不具合
```

「なぜ」には、引き継ぎで受け取った背景・課題・対応方針を書く。コミットメッセージと PR の「なぜ必要なのか？」はここから書く。

手順を1つ終えるたびに、チェックを付けて保存する。セッションの todo（TaskCreate）は表示用で、正は dev-flow.md にする。

手順を始めるときと終えるときに、その行の末尾へ時刻（`date +%H:%M`）を書く。時間のかかる手順を、あとから数字を見て縮めるため。

```markdown
- [x] 2. 実装とレビューを往復する（10:02〜10:41）
- [ ] 3. 動作確認の項目を決める（10:41〜）
```

## 手順

| # | やること | 呼ぶ skill | 次へ進む条件 |
|---|---|---|---|
| 1 | リポジトリの流儀を調べる | following-repo-conventions | 「流儀のメモ」が書けた |
| 2 | 実装し、レビューと往復する | herdr-coding | 直すと決めた指摘が残っていない。コミット済み |
| 3 | 動作確認の項目を決める | planning-manual-checks | 「動作確認」が書けた。「テストを足すもの」があれば手順 2 に戻してテストを足し、コミットしてから進む |
| 4 | 画面を撮る | capturing-screens（Sonnet のサブエージェントに任せる） | 「画面」の表が書けた。画面に変更がなければ飛ばす |
| 5 | 動作確認の動画を撮る | recording-manual-checks（Sonnet のサブエージェントに任せる） | 「画面」に動画のファイル名が書けた。4 を飛ばしたら飛ばす |
| 6 | draft PR を出す | creating-pull-requests | PR の URL が出た。dev-flow.md に書く |
| 7 | 画像と動画を PR に貼る | uploading-pr-media | PR の本文に表と動画が入った。4 を飛ばしたら飛ばす |
| 8 | Copilot の指摘に対応する | resolving-pr-reviews | 新しい指摘がなくなった |

動作確認の項目を撮影より先に決めるのは、動画をその項目に沿って撮るため。

飛ばした手順は、チェックを付けて「（飛ばした: 理由）」と書く。

画像と動画は PR に添付して上げるので、PR を出してから貼る。

## 待つあいだに進めること

手順は上の順に終えるが、待ち時間には次の手順の準備を進める。トークンを増やさずに、待ち時間だけを重ねられるため。裏で動かすコマンドは Bash の `run_in_background: true` で起動し、終わった知らせを待つ。

| 待っているもの | そのあいだに進めること |
|---|---|
| 最初の準備 | worktree の依存を入れる（`bundle install`・`yarn install` など、README に書かれたもの）。DB の migration はここではしない。DB はほかの worktree と共有していることがあるため |
| 1 の流儀を調べるサブエージェント | チケットと要件を読み、実装の方針を立てる |
| 2 の reviewer の返事 | 変えたところに関係するテストを流す。3 の項目の下書きを書く。画面を変えたなら、5 の動画の項目ごとのスクリプトを下書きし、撮影に使うアプリを起動する |
| 4・5 の撮影のスクリプト | 6 の PR のタイトルと本文を下書きする |
| 8 の Copilot の再レビュー | CI の結果を見て、落ちていれば直す（resolving-pr-reviews のステップ6） |

変更前の画面は、2 の実装に入る前に撮ってよい（capturing-screens の 3）。ベースブランチは作業の途中で変わらないため。

ファイルの編集も、同じ応答の中で Edit を並べて出す。サブエージェントに分けるのは、互いに関係しない機械的な変更が3ファイル以上あるときだけにし、`model: sonnet` にする。サブエージェントは起動のたびに要件と周りのコードを読み直すので、小さな変更では自分で書くより遅く、トークンも増える。

## 不具合を見つけたとき

撮影や動作確認のどこかで不具合を見つけたら、必ず直してから先へ進む。見つけたまま PR を出したり、動画を貼ったりしない。

```
不具合を見つけた
|-> 項目の書き方が間違い（名前違い・手順抜け）
|   `-> 項目を直して、その項目を撮り直す
`-> アプリの不具合
    `-> 下の 1〜4 の順に直す
```

1. dev-flow.md の「見つけた不具合」に、どの項目で、期待する結果と実際の動きがどう違ったかを書く。
2. 手順 2（実装とレビューの往復）に戻り、チェックを外す。herdr-coding で、まずその不具合を再現するテストを書いて落ちることを確かめ、それから直す。レビューを通してコミットする。同じ不具合が戻ってきたときに、CI で気づけるようにするため。
3. 直した項目の動作確認を撮り直し（recording-manual-checks で番号を渡す）、変わった画面のスクショも撮り直す。
4. 「見つけた不具合」の項目に「直した: <コミット>」と書いて、元の手順から続ける。

直し方に仕様の判断が要るときは、下の「止まるとき」に従う。

## 止まるとき

- 次へ進む条件を満たせないまま、同じエラーが2回続いた
- 要件や仕様の判断が要る

止まるときは、状態を `ユーザー待ち` にし、どの手順で何が足りないかを書いてから止まる。

全部の手順が終わったら、状態を `完了` にして、PR の URL を伝える。
