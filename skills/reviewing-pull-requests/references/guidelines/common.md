# すべての PR で見ること

どの PR でも読む。[../viewpoints.md](../viewpoints.md) の観点を、具体的に何で確かめるかの一覧。括弧の中は当てはまる観点と、ふつうの重さ。重さは目安で、壊れ方を根拠で示せるなら重くする。

チェックリストを上から全部当てるのではなく、差分に関係する項目だけを当てる。

## 既存のものとの重複

- 既存の機能・ライブラリ・ヘルパーと同じものを、新しく作っていないか（simplify、nit。同じ処理が食い違って動くおそれがあれば should）
- 既存のものを広げれば済むのに、別に作っていないか（simplify、nit）
- 名前の付け方とディレクトリの置き方が、近くの既存のコードと揃っているか（conventions、nit）

## テスト

- 変えた分岐のそれぞれを通るテストがあるか。正常な場合だけでなく、条件が外れる側と失敗する側も（tests、should）
- テストのデータが、実際に入りうる値になっているか。境界の値や、空・nil を含む（tests、nit）
- 「nil でない」「例外が出ない」のような弱い確かめではなく、期待する値そのものを確かめているか（tests、nit）

## セキュリティ

- パスワード・トークン・個人情報が、ログ・エラーメッセージ・応答に出ていないか（security、must）
- 新しく足した入口（画面・API・ジョブ）に、認証と権限の確認があるか（security、must）

## パフォーマンス

- ループの中で、DB や外部の API を1件ずつ呼んでいないか（code、件数が増えると目に見えて遅くなるなら should、そうでなければ nit）
- 結果を使わない計算や、同じ計算の繰り返しがないか（simplify、nit）

## エラー処理

- 外から来る値（リクエスト・ファイル・外部 API の応答）を、使う前に確かめているか（errors、壊れたデータが保存されるなら must）
- 利用者に見えるエラーメッセージが、何をすればよいか分かる文になっているか（errors、nit）

## 読みやすさ

- 名前が中身と合っているか（code、nit）
- 3段以上の入れ子を、早期リターンやメソッドの切り出しで浅くできないか（simplify、nit）
- 意味の分からない数値や文字列が、名前を付けずに書かれていないか（code、nit）
- 同じコードが繰り返されていないか（simplify、nit）

## 設計

- 1つのクラスや関数が、別々の理由で変わる仕事をいくつも持っていないか（conventions、nit）
- 外部のサービスやライブラリの呼び出しが、業務のロジックの中に直に書かれ、テストで差し替えられなくなっていないか（tests、nit）
- 条件分岐が増え続ける形になっていないか。種類ごとにクラスを分ける形で済まないか（simplify、fyi）
- 引数が多く、まとめて1つのオブジェクトにした方が分かりやすくないか（code、fyi）

設計の項目は好みが分かれる。リポジトリの CLAUDE.md・AGENTS.md や近くの既存のコードが採っている形に合わせ、採っていない形を持ち込む指摘はしない。

## リポジトリに入れるもの

- 画像・動画・PDF などの大きなファイルを、そのままコミットしていないか（code、should）
