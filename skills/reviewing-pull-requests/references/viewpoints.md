# レビューの観点

差分に当てる観点。reviewing-pull-requests と、reviewing-git-diffs の Codex のときの手順が使う。差分に関係する観点だけを当て、関係のない観点は飛ばす。

| 観点 | 当てるとき | 見ること |
|---|---|---|
| code | いつも | 条件の取り違え、nil・空・境界の値、並び順や重複、呼び出し元の想定との食い違い。細かい粗探しより、実際に踏む大きなバグを先に探す |
| errors | いつも | 例外の握りつぶし、失敗が呼び出し元に伝わるか、途中で失敗したときに中途半端な状態が残らないか、再試行で二重に処理されないか |
| tests | いつも | 変えた振る舞いを確かめるテストがあるか、テストが実装をなぞるだけになっていないか、失敗する場合のテスト |
| comments | いつも | 足したか変えたコメントやドキュメントが、実装と食い違っていないか、古くなっていないか。変えたファイルに前からあるコメントの注意書き（「ここは順番を変えない」「呼ぶ前に lock を取る」など）に、差分が沿っているか |
| types | 型・クラス・スキーマの定義が足されたか変わった | null を許すか、既定値、既存のデータとの整合、migration の戻し方 |
| security | いつも | 入力の検証、SQL・コマンド・HTML のインジェクション、認証・権限の抜け、秘密情報がログや応答に出ないか |
| simplify | いつも | 標準ライブラリで済む手書き、要らない依存、実装が1つだけの抽象化、使われていないコード |
| conventions | いつも | 名前空間・ディレクトリ・名前の付け方・粒度・テーブルの構成が、差分の近くの既存コードと揃っているか |
| guidance | リポジトリに CLAUDE.md か AGENTS.md がある | ルートと、変えたディレクトリとその親の CLAUDE.md・AGENTS.md に書かれたルールに、差分が反していないか。これらはコードを書く AI 向けの指示なので、レビューに当てはまらないものは飛ばす |
| history | いつも | 変えたファイルの最近のコミットを読み、そのコードがなぜ今の形なのか（直したバグ、わざと入れた分岐）を踏まえて、差分がそれを壊していないか |
| past reviews | 変えたファイルに、以前の PR で付いたコメントがある | 以前の PR でそのファイルに付いた指摘のうち、今回の差分にも当てはまるもの |

## 重さ

| 重さ | 当てはまるもの | reviewing-git-diffs の区分 |
|---|---|---|
| must | このまま merge すると、不具合・データの破損・セキュリティの穴・動かない機能になる | Critical |
| should | 今すぐは壊れないが、近いうちに不具合や大きな手戻りになる見込みが高い。テストの抜けもここ | Important |
| ask | 意図が分からず、問題かどうかを判断できないところ。作者に理由を聞く | Suggestions |
| nit | 読みやすさ・名前・小さな重複など、直さなくても動くもの | Suggestions |
| fyi | 直す必要はないが、作者が知っておくとよいこと（関わる仕組み、似た既存の実装、今後気をつける点） | Suggestions |

approve を止めるのは must と should だけで、ask・nit・fyi は止めない。ask は作者が答えるまで次のラウンドに持ち越し、fyi は返事が要らないので持ち越さない。

意図が分からないところを、推し量って must や should にしない。不具合になると根拠で示せないなら ask にし、`title` と `body` は疑問文で書く（「ここで在庫を戻さないのは、別のジョブで戻すためでしょうか？」）。

guidance の指摘は、ルールに明記されていることだけを挙げ、どのファイルのどの文に反するかを `evidence` に引用する。明記されたルールに反するものは should、反した結果が must に当たる不具合になるなら must にする。

迷ったら軽いほうにする。重く付けすぎた指摘は、作者がそのたびに説明を書くことになる。

simplify と conventions の指摘は、明らかに既存の流儀に反するもの以外は nit にする。削る指摘は探せばいくらでも出るので、重く付けると往復が終わらない。
